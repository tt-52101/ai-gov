## 一、认证链路 (validateGovToken)

### 1.1 代码路径

文件：`ai-gov-fusion/backend/internal/server/gov_handlers.go`

| 步骤 | 函数/位置 | 操作 |
|------|-----------|------|
| 1 | `extractBearerToken(r)` (L416-422) | 从 `Authorization: Bearer <token>` 头提取明文 Token |
| 2 | `validateGovToken(token)` (L432-496) | 完整校验链，见下 |
| 2a | L438-439 | **SHA-256 哈希**：`sha256.Sum256([]byte(token))` -> hex 编码 |
| 2b | L448 | **表查询**：GORM 查询 `gov_api_keys` 表，`WHERE key_hash = ?` |
| 2c | L456-462 | **密钥状态校验**：`key.Status != StatusActive` 拒绝（`StatusActive = "active"`，定义于 `types.go:19`） |
| 2d | L461-463 | **密钥过期校验**：`key.ExpiresAt != nil && time.Now().UTC().After(*key.ExpiresAt)` 拒绝 |
| 2e | L466-483 | **用户状态校验（禁人即禁Key）**：查询 `admin_users` 表 `WHERE id = key.OwnerUserID`，校验 `user.Status != StatusActive` 拒绝 |
| 3 | L486-487 | 校验通过后更新 `last_used_at` 字段 |
| 4 | L489-495 | 返回 `(userName, ownerUserID, true)`，SubjectID 为 `OwnerUserID`（而非 Key ID），因为 ABAC 策略绑定到用户 |

### 1.2 场景验证

| 场景 | Token 状态 | 用户状态 | 预期结果 | 代码依据 |
|------|-----------|---------|---------|---------|
| 管理员正常 Token | active / 未过期 | active (admin role) | **通过** - L456-462, L475-482 均通过 | `gov_handlers.go:435-495` |
| "已禁用用户" Token | active / 未过期 | **disabled** | **拒绝** - L475 检查 `user.Status != StatusActive`，命中返回 false | `gov_handlers.go:475-482` |
| "已过期" Token | active / **已过期** | active | **拒绝** - L461 检查 `time.Now().UTC().After(*key.ExpiresAt)`，命中返回 false | `gov_handlers.go:461-463` |
| "已吊销" Token | **revoked** | active | **拒绝** - L456 检查 `key.Status != StatusActive`，命中返回 false | `gov_handlers.go:456-458` |
| 无 Token | N/A | N/A | **拒绝** - `requireGovAuth` L217-219 返回 401 | `gov_handlers.go:217-219` |

### 1.3 审查结论

认证链路完整，五步校验链（SHA-256 哈希 -> 表查询 -> 密钥状态 -> 过期时间 -> 用户状态）无缺失。`StatusActive = "active"` 常量定义于 `types.go:19`，`AdminUser.Status` 字段定义于 `types.go:631`。

**注意**：SHA-256 哈希无加盐。对于 API Key 认证场景此为行业惯例（Key 本身具有足够熵），但若未来支持短口令则需加盐。

### 4.2 鉴权覆盖结果

**所有 47 个路由前缀均有 ABAC 鉴权调用**。每个 handler 至少有一条 `requireGovAuth` 或 `requireGovItemAuth` 调用路径，覆盖所有 HTTP 方法（GET/POST/PUT/PATCH/DELETE）。

### 4.3 代码质量问题：未检查 ABAC 返回值

大量 handler 使用了 `_, _ = h.requireGovAuth(...)` 或 `_, _ = h.requireGovItemAuth(...)` 模式（丢弃返回值）：

**涉及端点（所有使用 `_, _` 模式的 handler）**：
- Party 域：GET party-edges, DELETE party-edge, GET party-members, DELETE party-member
- Fund 域：GET accounts, GET account, GET account/ledgers, GET allocations, GET allocation
- Key 域：GET/DELETE/POST key item
- Pricing 域：GET model-prices, GET/DELETE model-price item
- ModelGrant 域：GET model-grants, GET/DELETE model-grant item
- Routing 域：GET route-profiles, GET/PUT/DELETE route-profile item, GET route-strategies, GET model-routes, PUT/DELETE model-route item
- ABAC 域：GET action-catalogs, GET roles, GET/PUT/DELETE role item, GET policies, GET/DELETE/POST policy item, GET subject-role-bindings, DELETE subject-role-binding, GET grants, DELETE grant
- UI Permission 域：POST/GET ui-menus, GET/PUT/DELETE ui-menu item, POST/GET ui-routes, GET/PUT/DELETE ui-route item, POST/GET ui-action-bindings, GET/PUT/DELETE ui-action-binding item
- Audit/Dashboard 域：GET audit-events, GET audit-event, GET request-logs, GET request-log trace, GET audit-chain-anchors, POST/GET reconciliation-runs, GET reconciliation-run, GET dashboard, GET security-reports, GET trace

**安全影响评估**：

当 `requireGovAuth` / `requireGovItemAuth` 鉴权失败时，函数内部已通过 `writeError(w, r, ...)` 向 HTTP ResponseWriter 写入错误响应（401 或 403）。但调用方未检查返回值并执行 `return`，导致 handler 继续执行并尝试写入第二次响应（成功响应或占位消息）。

在 Go `net/http` 中，第二次 `WriteHeader` 调用会被忽略（或 panic），第二次 `Write` 同样会被忽略。客户端实际收到的是第一次写入的错误响应（401/403）。因此：

- **ABAC 鉴权在功能上是生效的**（客户端无法绕过）
- **但存在代码健壮性问题**：多余的业务逻辑执行（如数据库查询）在鉴权已失败时浪费资源
- **日志混乱**：鉴权失败后仍会记录 "查询成功" 等误导性日志

相比之下，写操作 handler（CREATE/UPDATE/DELETE 等）大都正确使用了 `gctx, _ := ...; if gctx == nil { return }` 模式。这些端点安全性完备。

### 4.4 其他发现

1. **`handleUIPermissionSnapshot`**（L987-1018）调用 `requireGovAuth(w, r, "")` 传入了**空字符串 action**。`requireGovAuth` 在 action 为空时跳过 ABAC 评估（L222 `action != ""`），仅执行 Token 验证。这是合理设计——该端点根据已验证用户身份返回其可见菜单，权限过滤在 `ProjectMenus` 内部完成。

2. **`handleReconciliationRunItem`**（L1146-1156）对单品端点使用了 `requireGovAuth` 而非 `requireGovItemAuth`。这意味着 ABAC 资源 ID 传入的是 URL 路径而非实际 runID。当前此端点为占位实现（"阶段 D 实现"），功能补齐时需修正。

3. **`handlePartyEdgeItem`** 和 **`handlePartyMemberItem`** 的 `resourceType` 参数为 `"party_edge"` / `"party_member"`，但 `lookupResourceParty` 函数（L296-346）中未注册这两种资源类型的 party_id 查询映射，将走 default 分支返回空字符串。这导致这两个端点的 scope_party_id 过滤不生效——这是一个需要修复的 gap。
