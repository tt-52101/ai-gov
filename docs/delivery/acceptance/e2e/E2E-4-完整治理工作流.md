## 场景 1：登录 + 动态菜单（步骤 1-3）

### 步骤 1：财务人员使用 API Key 调用 `POST /gov/auth/login`

**判定：端点不存在 / 缺口**

**代码路径追踪：**

搜索全量代码库中所有路由注册：

```
ai-gov-fusion/backend/internal/server/http.go
  第 174 行: s.mux.HandleFunc("/api/admin/auth/login", s.handleAdminLogin)
  第 163 行: s.mux.HandleFunc("/v1/chat/completions", s.gatewayInFlight(s.pipelineChatHandler))
```

`RegisterGovHandlers` 函数（`gov_handlers.go` 第 110-179 行）管理的是 `/gov/*` 前缀的控制面路由，其列表不含 `/gov/auth/login`。现有的登录入口是 `/api/admin/auth/login`（`http.go` 第 2001-2028 行），其流程为：

```
handleAdminLogin (http.go:2001)
  -> decodeJSON: identity + password
  -> s.store.AuthenticateAdminUser(identity, password, 12h)
  -> 返回 {token, expires_at, user}
```

该端点使用用户名/密码认证，返回的是管理后台 Session Token，而非治理 API 的 Bearer Token。治理 API 本身无独立登录端点 -- 其 Bearer Token 鉴权通过 `validateGovToken`（`gov_handlers.go` 第 432-496 行）直接校验 `gov_api_keys` 表中的密钥哈希：

```
requireGovAuth (gov_handlers.go:198)
  -> extractBearerToken / X-API-Key Header
  -> validateGovToken(token): SHA-256 哈希 → 查 gov_api_keys → 校验 status/expiration/用户状态
  -> ABAC Engine.Evaluate(subject, action, resource)
```

**缺口说明：** 测试场景假设存在 `POST /gov/auth/login` 端点，但实际代码中不存在该路由。治理 API 采用的是预分发的 API Key 模式（Bearer Token/X-API-Key），无需运行时登录。需确认这是测试文档的表述偏差还是功能缺失。

### 步骤 3：菜单按 ABAC 评估结果过滤 -- 财务人员应看到"资金管理"但不看到"路由管理"

**判定：通过**

**实现逻辑分析：**

菜单过滤依赖两个层面：
1. **菜单级别**：`Projector.evaluateAnyRoute` 对菜单关联的路由逐一评估 `required_action_id` 对应的 ABAC 权限。若菜单无路由（容器菜单），则等待子菜单传播可见性。
2. **路由级别**：`Projector.ProjectRoutes` 基于 ABAC 评估判定每个路由是否可访问。

ABAC 引擎通过角色绑定 + 策略（deny 优先）判定权限。若财务人员角色绑定了 `fund.*` 权限但未绑定 `routing.*` 权限，则"资金管理"菜单（关联 fund 相关 action）可见，"路由管理"菜单（关联 routing 相关 action）不可见。

**结论：** 机制完整。实际行为依赖数据库中正确配置的角色、策略和菜单绑定。

### 步骤 16：清算后 Key 是否失效？

**判定：缺口**

**代码路径追踪：**

**Key 认证流程**（`gov_handlers.go:432-496`）：

```go
validateGovToken(token):
  1. SHA-256 哈希
  2. 查 gov_api_keys 表：WHERE key_hash = ?
  3. 校验 key.Status == "active" (或空)
  4. 校验 key.ExpiresAt 未过期
  5. 校验 owner_user (admin_users) 未被禁用
  6. 更新 LastUsedAt
```

**数据面调用认证**（`pipeline_handler.go:40`）：

```go
project, key, err := s.authenticate(r)
```

`authenticate` 方法验证 `api_keys` 表的密钥，通过 `key.AccountID` 关联到资金账户。

**清算对 Key 的影响分析：**

- **控制面 Key**（`gov_api_keys`）：`validateGovToken` 不检查关联账户状态。清算仅改变账户 `status` 和余额，不影响 `gov_api_keys` 表中的 Key 记录。
- **数据面 Key**（`api_keys`）：`authenticate` 验证密钥本身，不检查账户清算状态。但数据面 Pipeline 步骤 [8]（冻结）中 `fund.Service.Freeze` 会检查 `acct.Status != StatusActive` → 返回 `newAccountFrozenError`，间接阻止新调用。

**缺口说明：** 清算后 Key 不会自动失效（`status` 不会被设为 `revoked`），而是通过账户状态间接阻止新调用/冻结。被阻止的操作发生在 Pipeline 冻结步骤，而非认证步骤。这意味着：
- 已获取的 Bearer Token 在清算后仍可通过 `validateGovToken`
- 新的 API 调用会在冻结阶段（步骤 [8]）被拒绝（账户非 active）
- 没有清算后自动吊销 Key 的逻辑

**建议：** 可在 `liquidateStartNew` 中将关联 Key 批量设为 `revoked`，或在 `validateGovToken` 中增加账户状态检查。
