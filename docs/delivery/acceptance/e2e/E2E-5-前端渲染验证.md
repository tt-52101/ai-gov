## 四、前端路由守卫

### 4.1 布局结构

```
app/(console)/layout.tsx      -- AdminConsole (不渲染 children)
  └── app/(console)/gov/layout.tsx  -- GovLayout (ABAC 动态菜单，但不拦截路由)
        ├── /gov/dashboard
        ├── /gov/fund
        ├── /gov/parties
        ├── ... (8 modules)
```

### 4.2 守卫分析

**GovLayout** (`layout.tsx`) 只负责：
- 调用 `GET /gov/ui-permissions/snapshot` 获取菜单可见性
- 过滤侧边导航栏中显示的菜单项
- **不执行任何路由级别的权限拦截**

**关键发现：**

| 场景 | 行为 | 结论 |
|------|------|------|
| 用户直接访问 `/gov/fund`（URL 直接输入） | GovLayout 渲染完整布局，fund/page.tsx 正常挂载并调用 API | 无前端路由守卫 |
| API 调用因权限不足被后端拒绝 | `extractErrorMessage` 捕获 AUTHZ_DENIED，显示 "权限不足" | 服务端兜底 |
| 用户无 fund 菜单权限但直接访问 `/gov/fund` | 侧边栏 fund 菜单项不可见，但页面内容正常加载 | 页面未受保护 |
| 前端 `middleware.ts` | **不存在** -- 项目未配置任何 Next.js middleware | 无全局路由守卫 |

**还需要检查：** `(console)/layout.tsx` 中的 `AdminConsole` 组件**不渲染 `children`**（其函数签名不接受 children，JSX 中无 `{children}`）。这意味着 `(console)` 路线组下的所有子页面实际上不会通过该布局渲染。但 `/gov/*` 路由使用了 GovLayout 的子布局，实际渲染链路有待运行时验证。

### 4.3 结论

- 前端无全局 middleware 守卫
- GovLayout 仅过滤菜单可见性，不阻止页面渲染
- 无权限用户可通过直接输入 URL 访问任意 `/gov/*` 页面
- 服务端 API 调用会在用户无权限时返回 AUTHZ_DENIED（403），前端通过 ErrorAlert 展示 "权限不足"
- **风险等级：中等** -- 页面内容会短暂渲染后显示权限错误，而非直接重定向

**extractErrorMessage 回退逻辑：**
1. 尝试从 `res.json()` 中读取 `body.error.code`
2. 通过 `getErrorMessage(code)` 映射到中文文案
3. 如果映射失败，返回 `body.error.message`
4. 如果都失败，返回 "请求失败 (HTTP {status})"

### 5.2 关键场景验证

#### 场景 1：后端返回 BUDGET_CAP_EXCEEDED

```
后端响应: { error: { code: "BUDGET_CAP_EXCEEDED", message: "..." } }
  → extractErrorMessage() 读取 body.error.code
  → getErrorMessage("BUDGET_CAP_EXCEEDED") === "预算已达上限"
  → ErrorAlert 显示 "预算已达上限"
```

| 步骤 | 结果 |
|------|------|
| 错误码映射 | 通过 |
| 用户看到中文提示 | "预算已达上限" |

#### 场景 2：后端返回 AUTHZ_DENIED

```
后端响应: { error: { code: "AUTHZ_DENIED", message: "..." } }
  → extractErrorMessage() 读取 body.error.code
  → getErrorMessage("AUTHZ_DENIED") === "权限不足"
  → ErrorAlert 显示 "权限不足"
```

| 步骤 | 结果 |
|------|------|
| 错误码映射 | 通过 |
| 用户看到中文提示 | "权限不足" |

#### 场景 3：网络断开（fetch 抛出 TypeError）

```
fetch 调用 → 网络异常 → catch (err)
  → err.message 通常为 "Failed to fetch"
  → ErrorAlert 显示 err.message
  → 显示 "重试" 按钮（如有 onRetry）
```

**各页面 onRetry 支持情况：**

| 页面 | ErrorAlert 是否有 onRetry | 网络断开可重试 |
|------|--------------------------|---------------|
| dashboard | 有 (`onRetry={fetchDashboard}`) | 是 |
| fund | 有 (`onRetry={fetchAccounts}`) | 是 |
| parties | 有 (`onRetry={fetchParties}`) | 是 |
| pricing | 有 (`onRetry={fetchPrices}`) | 是 |
| routes | 有 (`onRetry={fetchProfiles}`) | 是 |
| **abac** | **无** -- 仅传入 `dismissible` (line 432) | **否** |
| **ui-permissions** | **无** -- 仅传入 `dismissible` (line 297) | **否** |
| audit | 有 (`onRetry={fetchEvents}`) | 是 |

**发现：** abac 和 ui-permissions 两个页面的 ErrorAlert 未传递 `onRetry`，网络断开后用户只能看到错误信息和关闭按钮，无法一键重试。这两个页面各自有独立的 fetch 函数（如 `fetchRoles`, `fetchPolicies`, `fetchMenus` 等），但由于它们共享一个 error 状态，设计上较难为绑定的 ErrorAlert 确定单一的重试目标函数。

## 六、关键发现与建议汇总

### 已实现且正确

1. 全部 8 模块的 page.tsx / loading.tsx / error.tsx 三件套完整
2. 全部页面使用 `extractErrorMessage` 统一处理 API 错误
3. ABAC 动态菜单：挂载时正确调用 `/gov/ui-permissions/snapshot`，visible=false/true/undefined 三种情况均正确处理
4. ABAC 故障降级三路径完整（非 2xx、空数据、网络异常）
5. abac 页面正确对 `is_system` 角色和策略隐藏删除按钮
6. parties 页面删除按钮存在（batch-003 修复确认生效）
7. 错误码映射覆盖 PRD 规范全部 25 个错误码
8. ErrorAlert 组件支持重试按钮和关闭

### 需关注的问题

1. **路由守卫缺失** -- 前端无 middleware，GovLayout 不拦截无权限路由访问；无权限用户可直接输入 URL 访问页面，页面先渲染后 API 失败才显示错误
2. **操作按钮无前端权限检查** -- fund 的"划拨"、"清算"按钮以及其他页面的创建/编辑/删除按钮均无条件渲染，仅在服务端 API 调用时拦截
3. **abac 和 ui-permissions 页面 ErrorAlert 缺少 onRetry** -- 网络断开后用户无法一键重试
4. **ABAC 页面错误状态跨 Tab 共享** -- 角色、策略、绑定三个 Tab 共用一个 `error` state，一个 Tab 的错误会残留到其他 Tab
5. **`(console)/layout.tsx` 不渲染 children** -- `AdminConsole` 组件是整个 TokenHub 管理台的自包含页面，其 JSX 中无 `{children}`，这意味着 `/gov/*` 路由的实际渲染链路有待运行时确认
