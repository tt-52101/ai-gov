# 第 0 章 文档说明与设计哲学

## 0.1 文档性质

本文是独立完整的产品需求规格与关键详细设计合并文本。不依赖其它会话或外部文稿补语义。覆盖：定位与公理、物理世界主体、开源融合、双轨计价、预算帽数据模型、错误码全表、模型权限与正交授权、资金/调度/冻结/清算/幂等、功能需求逐条表、数据纪律、架构与二次开发、非功能、验收、分期、门禁与交付物。

## 0.2 设计哲学与差异化定位

Token 是 AI 时代的电力，但 **99% 的企业还没装电表**。本产品不运营模型供给、不对外倒卖 Token，只做企业内部 AI 能源控制面——**智能电表、配电箱、财务结算中心**。

### 核心洞察

1. **Token ≠ 电力。** 同等数量的 Token 在不同模型下，价格、业务价值完全不同——简单累加式机械统计毫无意义，必须具备业务感知能力。
2. **厂商总账单 ≠ 企业内部分户电表。** 上游供应商只能提供账号级总额，无法关联企业内部组织架构。多厂商、多模型、异构计价规则下，多张账单难以统一核算。
3. **普通 API 中转工具**解决的是「请求能不能送达模型」；**企业 AI 网关**解决的是「AI 能源如何**计量、分配、管控、追溯**」。

### 产品提供的四大能力

1. 统一模型调用入口  
2. 精确计量与双轨计价  
3. 主体经费账本、划拨与清算  
4. 安全控制与不可抵赖审计  

### 行业趋势判断

随着 Agent 大规模落地、全员 AI 助手普及，Token 将从零散软件订阅支出变为企业持续性核心生产成本。企业关注点正从「模型单价」转向「**资源分配、投入产出、Token 使用效率**」。管理公理不变：无计量则无管理；无归因则无法优化；缺少自有 Token 网关，企业无法真正掌控 AI 资产。每家规模化企业，最终都会部署属于自己的 **Token 智能电表**。

**目标闭环：**

```text
模型接入 → 安全拦截 → 智能调度 → 实时扣费 → 资金回笼与清算 → 对账审计
```

## 0.3 核心公理（不可配置取消）

1. **无计量则无管理。**  
2. **无归因则无法优化。**  
3. **无企业自有调用入口则无法真正掌控 AI 资产与成本。**  
4. **无守恒账本则无财务治理护城河。**  
5. **调度不得改变扣费账户；内部结算价格受请求锚定与上浮上限约束；禁止先调用后欠费。**  
6. **数据范围、资金、身份密钥、调度与模型配置四轴正交授权；禁止一轴推导另一轴特权；模型可用范围与资金扣费主体必须解耦。**  
7. **平台管理员也必须经账本服务与流水变更余额，不得提供绕过守恒的后门接口。**

## 0.4 能力优先级（核心竞争力顺序）

| 优先级 | 能力域 | 说明 |
|--------|--------|------|
| **P0** | 统一接入与密钥托管 | 消灭野连接，全部调用经网关 |
| **P0** | **财务治理与计量闭环** | 双轨、账本、划拨清算、Key 扣费、预算帽分码、守恒流水——**第一护城河** |
| **P0** | 正交授权、数据不越权、模型访问治理 | 四轴 + ModelGrant |
| **P0** | 调度与资金强制边界 | 价格帽、账户锁定、禁止先调后欠费 |
| **P0** | 治理 API 与资金写幂等 | 与控制台对等，防重复记账 |
| **P1** | **可插拔路由策略矩阵与降本高可用** | 单策略启停、混合组合，非固化四层 |
| **P1** | 基础运营报表与仪表盘 | 消耗、余额、预算、拦截可见 |
| **P2** | 内容安全与出网强化 | 具体扫描引擎可后置 |
| **P2** | 配置变更快照强化、上游账单自动对账 | 等保与运营深化 |
| **架构 P0** | 数据面安全扩展点 | 阶段 B 预留钩子，避免后期全链路改造 |

合同强制合规时，可将 SEC 能力提升为该项目的 P0，不改平台资金内核。

# 第 1 章 产品综述

## 1.1 要解决的问题

1. 员工与团队私自采购上游 API Key，调用黑箱，无法统一禁用与审计。  
2. 财务只能拿到厂商总账单，无法按组织、项目、人员、应用做内部结算与毛利分析。  
3. 成本失控：无预算预扣、无实时阻断、无双轨；预算帽与「账户真没钱」若同一错误码则运营无法精细抓手。  
4. 合规风险：敏感数据可能经未审批路径出境；管理员改配置缺少不可篡改留痕。  
5. 可用性与成本：仅写死「主→备→降级→缓存」四层不足以支撑商业灵活组合；调度不受内部价格约束会击穿账本。

## 1.2 价值主张

| 主张 | 说明 |
|------|------|
| 统一治理 | 全部模型调用经单一企业网关，消灭野连接 |
| 财务闭环 | 主动预算、预扣与实扣、主体间划拨与清算、双轨计量、预算帽与余额不足分码、对账 |
| 安全合规 | 密钥托管、出网策略、内容安全、全链路与配置变更审计 |
| 降本增效 | 在准确计量与价格约束前提下，按可插拔策略矩阵做成本、健康、权重、亲和等调度 |

## 1.3 产品边界

**本产品负责：**

- 身份、成员、主体（组织与项目等）、正交授权、模型访问治理（ModelGrant）  
- 上游模型与私有化资源接入、上游密钥托管  
- 调用接入（OpenAI 兼容等）、安全拦截扩展点、可插拔路由调度  
- Token 计量、双轨计价、账本、划拨、预扣结算、预算帽、清算  
- 调用审计、配置变更审计、对账与成本报表  
- 管理控制台与对等的控制面治理 API  
- 运维可观测  

**本产品不负责：**

- Agent / 工作流编排、Skill 市场、面向终端用户的业务对话产品 UI  
- 作为云厂商对外售卖 Token 或模型本身（**未来可能支持，架构须预留多租户隔离与对外售卖扩展点**）  
- 同一请求拆分到多个账本分摊扣费  
- 默认透支信用（负余额作为正常成功路径）  
- 由业务客户端负责冻结续期  
- 以公链 / 联盟链作为热路径余额系统记录  

**与上层契约：** OpenAI 兼容 HTTP API（及必要其它协议兼容面）；业务标签（user/task/agent/skill 等）仅用于归因，**不替代**鉴权与扣费账户。

## 1.4 目标用户

| 角色 | 主要诉求 |
|------|----------|
| 平台管理员 / 架构师 | 部署、资源池、路由档案、系统配置、上游密钥、模型目录 |
| 财务 / 成本控制 | 账本、划拨、内部加价、预算帽、报表、对账、清算 |
| 安全 / 合规 | 出网、拦截、审计检索、保留策略 |
| 组织或项目负责人（Leader） | 本主体经费、成员与 Key、消耗可见、模型范围（在授权内） |
| 实体人（员工/外包） | 持有 Key、合法调用、查看本人用量 |

# 第 2 章 物理世界主体模型（Party 多态）

## 2.1 设计出发点

真实企业 AI 经费与编制形态是多态的。系统**不得**假设唯一结构「公司 → 部门 → 项目 → 人」，也**不得**强制「项目必须挂在某个部门下」。

## 2.2 典型场景（必须全部可落地）

| 场景 | 组织 | 项目 | 关系与资金 |
|------|------|------|------------|
| 部门日常额度 | 有常设部门 | 可不建项目 | 部门主体持有账本，人的 Key 扣部门账本 |
| 部门主责专项 | 有 | 有 | 可用 owns 关联；项目可自有账本 |
| 公司级战略项目 | 多个事业部 | 有，可与部门平级 | 多 sponsors 出资到同一项目账本；独立 Leader |
| 跨主体协作 | 内外部组织 | 有 | 人可只加入项目、不加入内部部门 |
| 矩阵制 | 产品线、区域等 | 有 | 多协作边；**一次调用只扣一个账本** |
| 结项还钱 | — | 结束 | 剩余资金回流；Key 失效或改绑 |

## 2.3 统一主体 Party

- **组织（org）与项目（project）同一层语义**，均可：持有账本、拥有成员、指定 Leader、作为授权资源。  
- **项目不必然从属于某个组织。**  
- 控制台可分「组织」「项目」导航，底层模型与权限引擎必须统一，避免两套账本、两套授权。

## 2.4 关系边

| 关系类型 | 含义 | 与资金的关系 |
|----------|------|----------------|
| parent | 组织汇报树上下级 | 默认允许**上级 → 下级**划拨 |
| sponsors | 出资 | 默认允许**出资方 → 被出资方**划拨 |
| owns | 主责 / 主办 | **不**自动产生划拨权 |
| participates | 协作 | **不**自动产生划拨权 |

无关系时：独立项目或独立组织费用池均可成立。

## 2.5 人、Key、账本、Leader

| 对象 | 物理对应 | 规则 |
|------|----------|------|
| Person | 实体人 | 通过成员关系进入一个或多个 Party |
| API Key | 消费凭证 | 必须绑定且仅绑定一个 `account_id`；调用与扣费的唯一入口；必须归属实体人 |
| Account | 小金库 | 归属某个 Party；可用余额与冻结金额 |
| Leader | 负责人 | 对本 Party 默认责任角色；权限仍以**显式 Grant**为准，禁止仅靠头衔万能 |

**资金流转强制规则：**

1. 划拨：一方减少、另一方增加，金额相等，同一事务。  
2. 预扣：可用余额转入冻结，必须带 `freeze_id` 与过期时间；预扣前可经预算帽校验。  
3. 结算：按实际内部价从冻结结清，多退少补。  
4. 清算：按状态机阻断新调用、排空冻结后回流资金并收口 Key。  
5. 任何余额变更必须有流水；禁止无流水改账；默认不允许成功路径产生负余额。  
6. 关键资金写操作必须支持幂等。

**消费强制规则：**

- 内部结算金额（sell）只从 **Key 绑定的账户**扣除，并归因到 **Key 所属实体人**。  
- 业务标签只做报表归因，**不形成第二套资金**。  
- 禁止「只扣项目、不记到人」。

## 2.6 可迭代与扩展原则

- **稳定核心：** 计量、双轨、账本守恒、Key 扣费、四轴授权、ModelGrant、统一入口、价格上限与账户锁定、冻结生命周期、清算状态机、治理 API 幂等、预算帽分码。  
- **扩展面：** 新关系类型、新 itemCode、新路由策略、价目分时、安全钩子、对账连接器、划拨白名单。  
- **存储纪律：** 热字段原子；复杂进 JSON；禁止无限加表加列。  
- **发布演进：** 可先只计量双轨再实扣；策略可 shadow 后再生效。

# 第 3 章 开源底座选型与能力融合

## 3.1 功能矩阵对比

| 维度 | TokenHub（astaxie/TokenHub） | AxonHub（looplj/axonhub） |
|------|------------------------------|---------------------------|
| 定位 | 企业私有 AI 网关：统一入口、项目 Key、路由、配额、用量归因、RBAC、审计 | 通用 AI 网关：多协议、强 Trace、细粒度成本、自适应负载 |
| 技术 | Go + 管理台；SQLite/PostgreSQL；OpenAI 兼容 | 渠道×模型价目；成本明细；多维负载 |
| 组织/项目 | 项目空间、成员、项目 Key、成本归因 | 相对偏通道与调用侧 |
| 路由 | 优先级、权重、失败回退、亲和、健康诊断 | 多维评分、故障转移、负载 |
| 计费 | 基础用量与成本管控 | **itemCode 级明细、flat_fee/usage_per_unit/usage_tiered、缓存分项、JSON 价目、costItems** |
| 私有化 | SQLite-first + PG 多实例明确 | 开源可私有化 |
| 本产品缺口 | 缺双轨、守恒账本、划拨清算、四轴、价格帽、预算帽、ModelGrant | 缺企业内 Party 资金闭环 |

## 3.2 选型结论

- **主仓库底座：TokenHub**——最小化二次开发路径。  
- **必须吸收 AxonHub：** 费用项编码与计算口径、三种（及以上）计价模式、渠道×模型 JSON 价目（含 schedule 思路）、请求级 costItems、缓存与输入拆分避免双计、多维负载/健康评分思想（纳入策略矩阵实现）。  
- 本产品在单轨成本之上强制 **cost（上游）/ sell（内部）双轨**。

## 3.3 路由：可插拔策略矩阵（替代固化四层）

产品早期若只规定「主模型 → 备用 → 降级 → 缓存」四层，**不足以**支撑商业高可用与灵活运营。

**引擎要求：** 策略可注册；对档案可单独启用/禁用；可混合组合（加权评分或优先级链）；「四层」仅作档案预设。

| 策略代码 | 名称 | 作用 | 是否允许禁用 |
|----------|------|------|----------------|
| S-PRI | 优先级分组 | 主备硬分组与顺序 | 可 |
| S-HEALTH | 健康与熔断 | 失败率、连续失败、冷却、半开 | 可 |
| S-WEIGHT | 权重与负载 | 按权重与历史负载分配 | 可 |
| S-AFFINITY | 会话亲和 | 同会话优先同一渠道 | 可 |
| S-COST | 成本感知 | 在价格合格集内偏向更低 sell 或 cost | 可 |
| S-LATENCY | 延迟感知 | TTFT 或端到端延迟 | 可 |
| S-ERROR | 错误率感知 | 近期成功率惩罚 | 可 |
| S-RATE | 限流感知 | 降低触达 RPM/TPM/429 的概率 | 可 |
| S-TAG | 业务标签 | 按请求 Tag 定向或加权 | 可 |
| S-COMPLIANCE | 合规网络 | INTERNAL_ONLY 等硬过滤 | **硬策略，不可对受限主体关闭** |
| S-CACHE | 缓存兜底 | 最后手段降级渠道 | 可 |

**档案示例：**

- `simple-failover`：PRI + HEALTH + 有限 WEIGHT（类四层）  
- `ha-cost`：PRI + HEALTH + WEIGHT + COST + AFFINITY  
- `compliance-strict`：S-COMPLIANCE 强制 + PRI + HEALTH  

所有档案在跑策略前必须经过**价格合格集过滤**与 **ModelGrant 过滤**；调度结果**不得修改** `account_id`。

# 第 4 章 双轨计价（对齐 AxonHub 代码事实）

## 4.1 费用项 itemCode 基线（可扩展）

| itemCode | 含义 |
|----------|------|
| prompt_tokens | 输入（须与缓存类拆分） |
| completion_tokens | 输出 |
| prompt_cached_tokens | 缓存读 |
| prompt_write_cached_tokens | 缓存写 |
| completion_reasoning_tokens | 推理类输出（若上游提供） |
| 厂商特定缓存 TTL 变体等 | 按扩展增加 |

> **预留扩展（v2.0.2 标注）：** 后续版本将增加多模态费用项——`image_count`（图片张数）、`image_resolution_tier`（图片分辨率档位）、`video_duration_seconds`（视频时长秒数）、`prompt_audio_tokens` / `completion_audio_tokens`（音频 Token）。当前版本仅覆盖文本 Token 维度，详见 v3.x 主线方案。

## 4.2 计价模式

| 模式 | 说明 |
|------|------|
| flat_fee | 按次固定费用 |
| usage_per_unit | 按单位用量（通常每 1M Token） |
| usage_tiered | 阶梯价格（分段累计） |
| usage_volume（可选吸收） | 总量落档后整单同一单价 |

> **预留扩展（v2.0.2 标注）：** 后续版本将增加 `amortization_fixed` 模式——对私有化部署的模型（如 vLLM 推理集群），支持按月/年固定成本摊销，而非按 Token 计量，解决私有化模型内部核算合理性问题。详见 v3.x 主线方案。

## 4.3 双轨

| 轨道 | 含义 | 用途 |
|------|------|------|
| cost | 上游成本 | 对账、毛利 |
| sell | 内部结算价 | 扣企业内账本 |

## 4.4 价目 JSON 结构（渠道 × 模型）

```json
{
  "items": [
    {
      "itemCode": "prompt_tokens",
      "cost": { "mode": "usage_per_unit", "usagePerUnit": "..." },
      "sell": { "mode": "usage_per_unit", "usagePerUnit": "..." }
    }
  ],
  "schedule": {
    "timezone": "Asia/Shanghai",
    "overrides": []
  }
}
```

计算口径对齐 AxonHub：输入与缓存拆分（如 PromptTokens − Cached − WriteCached 等），缓存单独计价。  
**禁止**用「模型能力多维度档位」替代费用项体系。

## 4.5 用量规范化

适配层：上游 usage → 内部 itemCode；缺失记 0 + `usage_incomplete`；禁止伪造；对账可分类。

# 第 5 章 预算帽配置数据模型（详细设计）

## 5.1 目标

在「余额不足」之外提供可低于 100% 余额的软预算上限；错误码与余额不足严格区分。

## 5.2 挂载点

预算帽挂在 **Account** 上。本定版不做 Key 级分帽。

## 5.3 字段（推荐 accounts 热字段，控表数量）

| 字段 | 类型 | 含义 |
|------|------|------|
| budget_limit_amount | DECIMAL NULL | 预算上限；NULL=未启用 |
| budget_warn_ratio | DECIMAL NULL | 告警比例（如 0.80）；只告警不阻断 |
| budget_period | VARCHAR NULL | none / calendar_month / calendar_day / custom |
| budget_period_start | TIMESTAMPTZ NULL | custom 起点 |
| budget_period_end | TIMESTAMPTZ NULL | custom 终点 |
| budget_consumed_amount | DECIMAL NOT NULL DEFAULT 0 | 本周期已确认 sell 消耗累计 |
| budget_version | BIGINT/INT | 配置乐观锁 |

## 5.4 规则

1. `budget_limit_amount IS NULL` → 不做帽校验。  
2. 上限可小于当前 balance（软帽）。  
3. 告警：`budget_consumed_amount / budget_limit_amount >= budget_warn_ratio` → 通知，不拒绝调用。  
4. 阻断：`budget_consumed_amount + 本次预估 sell > budget_limit_amount` → **`BUDGET_CAP_EXCEEDED`**。  
5. 周期任务重置 consumed 并写审计事件。  
6. 结算成功的 sell 计入 consumed；解冻未消费不计入。  
7. 修改预算帽：fund 轴 `budget.write`；before/after 审计。

## 5.5 预扣判定顺序

```text
ModelGrant
  → 构建候选 → 价格合格集过滤
  → 若启用预算帽：帽校验（失败 → BUDGET_CAP_EXCEEDED）
  → 可用余额 ≥ 冻结额（失败 → INSUFFICIENT_BALANCE）
  → 写入 freeze
  → 策略矩阵选路 → 上游调用 → 结算
```

# 第 7 章 模型权限治理与正交授权（专章）

## 7.1 四轴分离

| 轴 | 回答的问题 | 禁止推导 |
|----|------------|----------|
| data | 能看哪些日志/报表/成员 | 不能推导可划拨、可改路由 |
| fund | 余额流水、划拨清算、预算帽 | 不能推导未授权 Party 全量日志 |
| iam | 人、Key、成员、禁人 | 不能绑无权账户；不能改价目 |
| routing | 价目、档案、策略、渠道、上游密钥、模型目录与 ModelGrant | 不能改 account_id；不能划拨 |

**调用链顺序原则：** 鉴权 Key → ModelGrant → 价格合格集 → 预算帽 → 冻结 → 调度（不改账户）→ 上游 → 结算。

## 7.2 模型访问治理

| 层次 | 含义 |
|------|------|
| 目录层 | 哪些逻辑模型对谁可见 |
| 调用层 | 谁允许发起对某模型的请求 |
| 合规层 | INTERNAL_ONLY 等硬限制 |
| 资金层 | 允许调用仍可能预算帽/余额失败 |

**逻辑模型 Model** → **渠道绑定 ChannelBinding** → **ModelGrant**。

### ModelGrant 字段

| 字段 | 含义 |
|------|------|
| principal_type | party / person / key / role |
| principal_id | 对应 ID |
| model_id 或 model_tag | 单个模型或标签组 |
| effect | allow / deny |
| priority | 冲突解析辅助 |

**冲突与默认（实现必须固定并验收）：**

- **deny 优先于 allow。**  
- 级联建议顺序：Key > Person > Party > 全局默认（写死一种）。  
- 商用推荐显式 allow 列表。  
- **禁止**仅因 Leader 头衔自动拥有全平台模型调用权。

## 7.3 Grant 最小动作矩阵

| 轴 | 动作 | 资源与约束 |
|----|------|------------|
| fund | balance.read, ledger.read | account / party |
| fund | allocate | 源账户；目标须满足划拨通道 |
| fund | liquidate | party / account |
| fund | budget.write | account / party |
| data | usage.read, report.read, member.read | 按 party/人/key 过滤 |
| iam | key.create / revoke / rotate | 绑户 ∈ 允许账户集合 |
| iam | user.disable | 授权范围内的人；联动 Key 失效 |
| iam | member.add / remove | party |
| routing | price.write | 价目 |
| routing | route_profile.write | 档案、策略、δ（≤20%） |
| routing | channel.write | 渠道资源 |
| routing | upstream_secret.write | 上游密钥仓库 |
| routing | model_catalog.write, model_grant.write | 目录与模型授权 |

## 7.4 数据不越权

- 所有列表/详情/导出按 data 轴 resource 过滤。  
- 禁止仅凭知道 UUID 读取未授权 Party 数据（防 IDOR）。  
- 余额流水归 fund，用量日志归 data，可只授其一。

## 7.5 调度正交

- 路由档案、策略、δ、渠道选择**不得**写入或改写 `account_id`。  
- S-COST 只在**模型授权合格且价格合格**候选集内排序。  
- 平台 admin 改路由 ≠ 自动获得划拨权。

## 7.6 验收红线清单

1. 无流水改余额  
2. 划拨无通道（非 parent 向下 / 非 sponsors 方向 / 非白名单）  
3. Key 无 account 调用  
4. 调度改扣费账户  
5. 先调后欠费（价格帽外候选仍调用）  
6. Leader 无 Grant 即全平台数据/资金/模型权限  
7. iam 建 Key 绑到无权账户  
8. 预算帽与余额不足返回同一错误码  
9. ModelGrant deny 后仍可调用该模型

# 第 8 章 关键边界规则与流程

## 8.1 预扣、价格约束与结算

1. **请求锚定内部价 \(P_{request}\)**：逻辑模型 + 价目 + 预估用量 → 内部 sell 预估金额。  
2. **候选价格约束：** \(P_{candidate} \le P_{request} \times (1+\delta)\)；**默认 δ=0**；**硬上限 20%**；超过上限的配置拒绝保存；**δ 的任何修改必须记关键配置变更审计**（操作者、档案 ID、前后值、时间）；不合格候选剔除；合格集为空 → `NO_ROUTE_WITHIN_PRICE_CAP`，**不得发起上游调用**。  
3. **ModelGrant** 失败 → `MODEL_ACCESS_DENIED`。  
4. **预算帽**（若启用）失败 → `BUDGET_CAP_EXCEEDED`。  
5. **冻结金额** = 价格合格候选集上预估 sell 的**最大值**；可用余额不足 → `INSUFFICIENT_BALANCE`。  
6. **调度**仅在合格集执行；**account_id 在鉴权时锁定，调度不得修改**。  
7. **结算**按实际用量与落地价目算 cost/sell；多退少补；冻结失效走补偿流水 + 告警，禁止静默丢账。

## 8.2 划拨路径规则

| 路径 | 默认是否允许 | 方向 |
|------|--------------|------|
| parent | 是 | 仅上级 → 下级 |
| sponsors | 是 | 仅出资方 → 被出资方 |
| owns / participates | 否 | 不自动开通 |
| 无关系双方 | 否 | 除非白名单 + fund |

平级任意互转默认禁止。清算回流在清算操作中显式指定目标账户，须 fund 授权与审计。

## 8.3 冻结生命周期与流式续期

1. 每笔冻结：`freeze_id`、账户、金额、`expires_at`、关联 request_id。  
2. **默认初始 TTL：15 分钟**（可配置，须有上下限，例如单次窗口 1–60 分钟）。  
3. **续期责任在网关，不在业务客户端。**  
   - 非流式：TTL 内完成或超时解冻。  
   - **流式（stream=true 或等价）：** 网关在流进行期间自动延长同一 `freeze_id` 的 `expires_at`；**不增加冻结金额**；累计有效期上限可配置（如不超过 2 小时）。  
4. 后台扫描过期冻结：自动解冻，流水类型为超时解冻。  
5. 以持久化记录为准。

## 8.4 清算状态机

```text
active
  → liquidating_block_new     // 拒绝新调用与新冻结；在途可继续
  → liquidating_drain         // 等待活跃冻结清零或全部过期解冻
  → liquidating_transfer      // 余额转入目标账户
  → liquidated                // Key 吊销或解绑；主体只读
```

存在未到期冻结时，不得将冻结占用金额当作可划转余额。可配置最长等待；超时仍有冻结则告警并停留 drain。

## 8.5 调用主路径

1. 客户端使用网关 Key 调用。  
2. 校验 Key、归属人未禁用、已绑定账户。  
3. 安全钩子（若启用）。  
4. ModelGrant。  
5. 计算 \(P_{request}\)；候选；价格过滤。  
6. 预算帽（若配置）；冻结。  
7. 策略矩阵选路；托管上游密钥调用。  
8. 流式场景网关续期冻结。  
9. 规范化用量；计算 cost/sell；结算；写调用审计。  
10. 返回兼容响应；错误码按第 6 章区分。

## 8.6 划拨路径

fund 授权 → 通道校验 → 幂等键 → 事务内双边记账与流水 → 操作审计。

## 8.7 治理 API 幂等

| 项 | 规则 |
|----|------|
| 适用范围 | 划拨、清算、资金补偿等会导致余额或主体资金状态变化的写接口 |
| 机制 | 客户端 `Idempotency-Key`（建议 UUID v4，≤255）；服务端对 (scope, actor_id, key) 去重 |
| 存储 | request_hash、status（started/succeeded/failed）、响应语义、resource_ref、expires_at |
| 抢占 | INSERT ON CONFLICT 原子抢占；禁止先 SELECT 再 INSERT |
| 行为 | 同键同指纹重放首次结果；异指纹拒绝；窗口建议 ≥24 小时 |
| 参考 | Stripe 类语义 |

## 8.8 账本技术选型

- **热账本：** PostgreSQL / TiDB / OceanBase 等强事务库；accounts + 只追加 ledgers。  
- **不采用**公链、联盟链作为热路径余额与划拨主账本。  
- **可选增强：** 流水禁止业务 UPDATE/DELETE；定期哈希摘要归档 WORM。

## 10.5 架构原则（v2.0.2 恢复）

以下 6 条原则是产品治理哲学在架构层的表达，任何技术决策不得违背：

| # | 原则 | 含义 |
|---|------|------|
| 1 | **厂商中立** | 不属于任何模型厂商，企业完整持有自身调用数据、计量规则、审计记录。模型供应商可迭代更换，企业治理体系持续可控。 |
| 2 | **治理优先，转发为辅** | 区别于普通 API 代理，首要目标是计量、管控、归因，其次才是模型路由转发。 |
| 3 | **财务可翻译** | 调用数据必须能翻译成财务可理解的成本与结算信息——把技术层面的 Token 调用转化为管理层可读的业务成本数据。 |
| 4 | **私有化优先** | 支持部署在内网边界，满足数据合规要求；支持离线/内网环境、国产 CPU 与操作系统。 |
| 5 | **核心路径短** | 核心扣费与授权路径保持最短；扩展通过策略插件、适配器、价目 JSON 与安全钩子完成，不破坏守恒与授权语义。 |
| 6 | **热账本 ACID** | 余额与流水热路径采用 PostgreSQL / TiDB / OceanBase 等强事务关系库，不以区块链/联盟链作为热路径余额系统记录。可选哈希摘要归档 WORM 用于审计增强。 |

# 第 11 章 系统架构与二次开发指导

## 11.1 逻辑架构

```text
应用/Agent → 兼容 API
  → Key 鉴权 → 安全钩子 → ModelGrant
  → 锚定内部价 → 价格合格集 → 预算帽 → 冻结
  → 策略矩阵选路 → 上游（托管密钥）
  → 用量规范化 → 双轨结算 → 审计

控制面：Party、Grant、划拨清算、预算帽、价目、路由、密钥、ModelGrant、治理 API（写幂等）
存储：ACID SQL 热账本（非区块链）
```

## 11.2 包划分（TokenHub 上扩展）

`fund`、`pricing`、`idempotency`、`party`、`authz`、`routing`、`modelgrant`、`security`。

数据面管道中间件化，避免逻辑堆单文件。

## 11.3 技术栈

Go；PostgreSQL/TiDB/OceanBase；Redis 可选；K8s；国产 CPU/OS **阶段 A 冒烟**。

## 11.4 幂等实现要点

表 `idempotency_records`：scope、actor_id、idempotency_key、request_hash、status、response、expires_at；UNIQUE(scope, actor_id, idempotency_key)；原子 INSERT 抢占。

## 11.5 策略引擎要点

```text
interface Strategy { Filter/Score(ctx, candidates) }
Profile: 启用策略列表 + 配置
Pipeline: candidates → COMPLIANCE → ModelGrant → price cap → strategies → pick
```
