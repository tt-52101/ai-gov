# 资金守恒定律覆盖性审计

**总评：** 在「单库 SQL 权威账本 + 本地事务划拨/冻结/结算 + 禁 2PC/禁 Redis 记账」前提下，**主路径守恒设计是闭合的**，足以支撑 PRD 财务闭环。仍存在若干**边界与运营层缺口**——不是颠覆公理，但若不在实现/运维上收口，会形成漏洞或对账死角。

---

## 1. 已覆盖且设计闭环的部分

| 定理/规则 | 覆盖点 | 闭合方式 |
|-----------|--------|----------|
| 划拨等额双边 | Allocate 同事务两账户 ±A + 双边 ledger | PG/SQLite 本地事务 |
| 无流水不改余额 | 禁止直接 UPDATE balance 的业务 API | 服务层只走 FundService |
| 预扣不丢可用语义 | freeze：frozen↑，balance 不变；available=balance−frozen | 状态字段 |
| 结算多退少补 | settle 对 freeze_id 结清 | 单笔冻结单次终态 |
| 超时释放 | TTL 扫描 → unfreeze + 流水 | SQL 权威，Redis 仅提示 |
| 幂等防双花 | 划拨/清算 Idempotency-Key | 唯一约束抢占 |
| 通道防乱转 | parent 向下 / sponsors 方向 / 白名单 | 记账前校验 |
| 清算不与在途打架 | block_new → drain → transfer | 状态机 |
| 调用不改扣费主体 | account_id 鉴权锁定 | 与调度正交 |
| 价格帽防先调后欠 | 合格集过滤后再冻 | 无合格集不调上游 |
| 预算帽 vs 真没钱 | 分错误码 | 判定顺序固定 |
| 多实例 SQLite | 禁止多写共享 SQLite | 启动校验 |
| Redis 不参与守恒 | 仅缓存/限流/提示 | 宕机降级仍信 SQL |

这些点串起来，**日常「划拨 → 人 Key 消费 → 清算」主链没有明显守恒空洞**。

---

## 2. 仍存的死角 / 漏洞（按严重度）

### 2.1 高：调用成功但结算失败（孤儿消费）

- **现象：** 上游已生成并计费，本地 Settle 因进程崩溃、DB 瞬时失败未完成；随后 TTL 把 freeze 解冻。  
- **守恒：** 系统内余额回滚了，**真实上游成本已发生** → 企业账与上游账单不一致。  
- **现状：** 文档提到 `settle_orphan` + 告警，但**不是自动守恒，而是补偿/人工**。  
- **收口建议（实现必做）：**  
  - 结算与「调用成功标记」尽量同逻辑可重试；  
  - 以 request_id 做结算幂等；  
  - 定时对账：有成功调用日志无 settle 流水 → 自动补 settle 或工单；  
  - 监控 `orphan_settle` 为零目标。

### 2.2 高：冻结金额 vs 实际 sell 的差额与并发

- 预估冻 max(候选)，实扣 sell 可能更低（多退）或在 δ>0 时更高。  
- δ=0 时设计上实扣 ≤ 锚定预估，一般 ≤ 冻结；若用量远超预估（长文、工具循环），**实扣可能 > 冻结**。  
- **漏洞：** 若 Settle 只从 frozen 扣、禁止动用额外 available，会结算失败；若静默再扣 available，需额外流水语义。  
- **收口：** 明确策略三选一并写死：  
  1. 超额从 available 补扣（ledger `settle_extra`）；  
  2. 超额失败并告警（可能已调上游 → 回到孤儿问题）；  
  3. 预估按更保守 token 上限冻结（产品策略）。  
  **推荐：1 + 用量上限拦截（请求 max_tokens 等）降低尾部风险。**

### 2.3 中：流式续期与累计 TTL 上限

- 续期不增金额；触顶后行为若只停续期、流仍在跑，可能再次出现「调用成功、冻结已过期」。  
- **收口：** 触顶策略写死：停流 / 强制结束并 settle / 进入 orphan 流程；与网关流控一起测。

### 2.4 中：清算 drain 超时

- 长期卡在 `liquidating_drain` 时余额不能转走，业务上「死锁感」。  
- 守恒未破，但是**运营死角**。  
- **收口：** 超时告警 SLA、强制处理手册（等 TTL、或人工标记 orphan 冻结）。

### 2.5 中：管理员/SQL 旁路

- 公理要求无后门，但 DBA 仍可直接改表。  
- **收口：** 账号权限、流水表禁 UPDATE/DELETE、定期 `sum(ledger)` 与 `balance` 对账作业、异常告警。

### 2.6 中：预算消耗累计口径

- `budget_consumed` 与结算异步若不一致，会出现「帽未触但应触」或反向。  
- **收口：** 优先与 settle **同事务**更新 consumed；周期切换任务与审计事件。

### 2.7 低：精度与币种

- SQLite/REAL 或浮点会导致分厘误差。  
- **收口：** 金额一律 decimal 字符串或定标整数；单币种先锁定。

### 2.8 低：部分失败的「通知类」副作用

- 划拨成功、Outbox 通知失败 → 不影响守恒，但运营以为失败。  
- **收口：** Outbox 重试，不以通知成功为事务条件。

### 2.9 低：跨库/分片账户（未来）

- 当前明确不做；一旦账户分库，现有本地守恒不够。  
- **收口：** 仅扩展点文档，不做实现；上线前禁止分片账户。

### 2.10 权限与通道配置错误

- 白名单过宽、Leader 模板过权 → 合法但「错转」。  
- **收口：** 默认最小通道、变更审计、定期权限回顾（治理问题，非公式漏洞）。

## 3. 守恒边界图（有无死角）

```text
[系统内 SQL 账本]
  划拨 ±A ──────────────────────── 闭合
  冻结/解冻（frozen 增减）────────── 闭合（available 守恒视角需含 frozen）
  结算（冻结→实扣）──────────────── 闭合（在 freeze 有效且实扣≤可补策略下）
  清算 transfer ─────────────────── 闭合（drain 完成后）

[系统外]
  上游已计费 vs 本地未 settle ───── 缺口 → 必须 orphan 补偿/对账
  上游账单与 cost 口径差 ─────────── 对账域，非余额公式
```

完整「企业现金 + 上游应付」视图 = **系统内守恒 + 上游对账与 orphan 闭环**。只宣称系统内 balance 守恒，**不能**自动等于「无财务损失」。

---

## 4. 是否「整体系统无死角」？

| 范围 | 判断 |
|------|------|
| PRD 定义的系统内账本守恒（划拨/冻结/结算/清算） | **基本完整**，实现按文档做可无公式级漏洞 |
| 含上游调用的端到端「钱与事实一致」 | **不完整**，依赖 orphan 结算、对账、超额 settle 策略 |
| 运维与人因（手改库、权限过大） | **需制度 + 对账作业**，单靠代码公理不够 |
| 多库/Redis 账本/2PC | 已排除，不引入新死角；扩展时需另开设计 |

---

## 5. 建议补进实现的「守恒收口清单」（最短）

1. **Settle 幂等（request_id / freeze_id）+ 成功调用补结算作业。**  
2. **实扣 > 冻结：明确补扣 available + ledger 类型。**  
3. **流式 TTL 触顶：强制结束路径与 settle/orphan 之一。**  
4. **日对账：account.balance vs 流水重放；冻结悬挂；调用成功无 settle。**  
5. **ledger 禁止业务删改；DBA 权限分离。**  
6. **budget_consumed 与 settle 同事务。**  
7. **金额 decimal；多实例禁用 SQLite 写共享。**  

---

## 6. 一句话结论

- **系统内资金守恒定律（单库本地事务方案）对主设计是完整、可落地的，没有故意留白的公式漏洞。**  
- **真正死角在「上游已发生 vs 本地未入账」以及「预估冻结 vs 实际用量」尾部**，必须用 **幂等结算、orphan 补偿、对账作业和超额策略** 补齐，否则商用仍可能出现账实不符。  
- 按第 5 节收口后，可认为在当前架构选型下达到 **可审计、可对账、可运营的守恒闭环**；在此之前不宜宣称「无死角」。
