# 完整守恒收口清单：设计说明

目标：在「SQL 单库本地事务权威账本」之上，把系统内守恒延伸为**可对账、可补偿、可运营的端到端闭环**，覆盖孤儿结算、超额实扣、流式 TTL 触顶、日对账、流水防篡改、预算累计一致性与金额精度。

---

## 0. 收口总览

| 编号 | 收口项 | 要解决的缺口 |
|------|--------|----------------|
| C1 | Settle 幂等 + 成功调用补结算 | 上游已成功、本地未入账 |
| C2 | 实扣 > 冻结时的补扣策略 | 预估不足、用量超冻 |
| C3 | 流式 TTL 触顶策略 | 续期到顶后仍在出字 |
| C4 | 日对账作业 | 静默漂移、悬挂冻结、孤儿调用 |
| C5 | Ledger 防篡改与权限 | DBA/旁路改余额 |
| C6 | budget_consumed 与 settle 同事务 | 预算帽误判 |
| C7 | 金额 decimal + 部署约束 | 精度与多实例 SQLite |

实现上全部落在 `fund` / `pricing` / 数据面管道与定时任务，**不引入 Redis 账本、不引入 2PC**。

## C1：Settle 幂等 + 成功调用补结算

### C1.1 状态与关联键

每次数据面请求固定：

- `request_id`（全局唯一）  
- `freeze_id`（有预扣时）  
- 调用结果：`upstream_ok` / `upstream_fail` / `unknown`

用量日志（或 `request_logs`）最小字段：

| 字段 | 含义 |
|------|------|
| request_id | 主键或唯一 |
| freeze_id | 可空 |
| account_id | 扣费账户 |
| upstream_status | success / error / timeout / unknown |
| settle_status | none / settled / orphan_pending / orphan_settled / settle_failed |
| sell_amount / cost_amount / cost_items | 可后写 |
| usage_incomplete | bool |

### C1.2 Settle 幂等规则

```text
Settle(freeze_id | request_id):
  以 freeze_id 为主键抢占（UPDATE freezes SET status='settling' WHERE id=? AND status='open'）
  若已 settled → 返回首次结果（幂等成功）
  若 timeout_released → 走 C1.4 孤儿路径，不二次解冻
  正常：按 C2 计算实扣 → 更新 balance/frozen → ledger → freeze=settled
  回写 request_logs.settle_status=settled
```

允许用 `request_id` 做第二幂等键：`UNIQUE` 或 settle 流水上带 `request_id` 唯一（成功结算类）。

### C1.3 主路径

```text
Freeze → 上游 →
  成功：NormalizeUsage → Calculate → Settle(幂等)
  失败：Unfreeze(freeze_id) 或 标记取消
  进程崩溃：既不 Settle 也不 Unfreeze → 依赖 TTL 与 C1.4
```

### C1.4 补结算作业（Orphan Reconciler）

**触发：** 定时（如每分钟）+ 可选启动时扫描。

**选中条件（示例）：**

```text
upstream_status = success
AND settle_status IN ('none', 'orphan_pending', 'settle_failed')
AND created_at < now() - interval '1 minute'   -- 避开进行中
```

**动作：**

1. 若 freeze 仍 `open` → 直接 `Settle`。  
2. 若 freeze 已 `timeout_released` / 不存在 → `OrphanSettle`：  
   - 从 **available** 扣 sell（见 C2 补扣语义）  
   - ledger 类型：`settle_orphan`  
   - 成功：`settle_status=orphan_settled`  
   - available 不足：`settle_status=orphan_pending`，告警，**不静默丢弃成本**（可记 `orphan_debt` 表或账户负向挂账策略，默认**禁止自动负余额**，改为工单）。  
3. 全流程幂等：同一 `request_id` 只成功入账一次。

### C1.5 监控

- `fund_orphan_pending_count`  
- `fund_settle_retry_total`  
- 告警：pending > 0 超过 N 分钟。

## C2：实扣 > 冻结时的补扣策略

### C2.1 定版策略（写死为推荐默认）

**主策略：冻结内先扣 + 超额从 available 补扣。**

```text
charged = sell_amount
from_frozen = min(freeze.amount, charged)
from_available = charged - from_frozen

若 from_available > 0:
  若 available < from_available → 补扣失败分支（见下）
  否则 balance -= charged, frozen -= from_frozen
  ledger:
    - settle_from_freeze (from_frozen)
    - settle_extra (from_available)   # 可合并一笔，type 区分明细
```

同时：**请求侧尽量限制** `max_tokens` / 预估乘安全系数，降低超额频率。

### C2.2 补扣失败（已调通上游）

与孤儿类似：

1. 尽可能扣尽 available，差额记 `orphan_pending` + 告警。  
2. **默认不自动 balance 变负**（符合 PRD）。  
3. 财务可人工划拨补足后重跑补结算作业。

### C2.3 与预算帽

- 预扣阶段已用**预估**过预算帽。  
- 实扣更高时：`budget_consumed` 按**实扣 sell** 增加（C6）；若实扣导致「本应触帽」——属预估误差，**不回溯拒绝已发生调用**，只在后续请求触帽。

### C2.4 单测要点

- sell < 冻：多退（frozen 释放差额）。  
- sell = 冻：正好。  
- sell > 冻且 available 足够：补扣成功、两类型流水。  
- sell > 冻且 available 不足：pending + 告警，不负余额。

## C3：流式 TTL 触顶策略

### C3.1 参数

| 参数 | 建议默认 |
|------|----------|
| freeze_default_ttl | 15m |
| freeze_renew_step | 2m（每步延长） |
| freeze_max_total | 2h（单次请求累计） |

### C3.2 触顶行为（定版）

当 `now + renew_step > freeze_created + freeze_max_total`：

1. **停止续期**；  
2. **中止上游流**（取消 context / 关闭下游）；  
3. 对**已收到**的 partial usage 做 Normalize + Calculate；  
4. 立即 `Settle`（或 usage 未知则保持 open 至短宽限后 orphan 流程）；  
5. 向客户端返回可识别错误/截断语义（如 `FREEZE_TTL_EXCEEDED` 或带 finish_reason）。

禁止：触顶后仍长时间出字且冻结已过期无人 settle。

### C3.3 实现要点

- 续期只 `UPDATE freezes SET expires_at=? WHERE id=? AND status='open'`，不改 amount。  
- 续期与触顶判断在网关流式循环内，**不依赖 Redis**。

## C4：日对账作业

### C4.1 作业列表

| 作业 | 频率建议 | 内容 |
|------|----------|------|
| R1 余额重放 | 日 / 可小时 | 对抽样或全量账户：`初始0+Σledger` 与 `balance/frozen` 比对 |
| R2 冻结悬挂 | 5～15 分钟 | `open` 且 `expires_at` 过期未处理 |
| R3 孤儿调用 | 1～5 分钟 | C1.4 条件 |
| R4 双边划拨 | 日 | 同 `idempotency_key` 或时间窗 `allocate_out` 合计 = `allocate_in` 合计 |
| R5 预算 | 日 | `budget_consumed` 与周期内 settle 类流水合计 |

### C4.2 差额处理

- 写 `reconciliation_findings`（薄表或日志）：account_id、type、expected、actual、status。  
- 自动可修：R2 触发 UnfreezeTimeout；R3 触发 OrphanSettle。  
- 不可自动：R1 结构性差额 → 告警人工（防静默改数）。

### C4.3 表（可选，控膨胀）

```sql
CREATE TABLE reconciliation_findings (
  id          BIGSERIAL PRIMARY KEY,
  job_type    VARCHAR(32) NOT NULL,
  ref_id      VARCHAR(128),
  payload     JSONB NOT NULL,
  status      VARCHAR(16) NOT NULL DEFAULT 'open', -- open|resolved|ignored
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

## C5：Ledger 防篡改与权限

### C5.1 数据库层

- 业务角色：`INSERT` 允许，**禁止 UPDATE/DELETE on ledgers**（REVOKE）。  
- 可选触发器：拒绝 UPDATE/DELETE。  
- accounts 余额变更仅来自执行 FundService 的 DB 用户；应用仅用该用户。

### C5.2 应用层

- 不提供「修改流水」「直接改 balance」API。  
- 冲正用**新流水**（如 `allocate_reverse`、`adjust` 需 fund 高权限 + 审计）。

### C5.3 可选增强（非必须本期）

- 每 N 条或每日对 ledger 做哈希链写入 `ledger_checksums`。  
- 备份与 PITR 按运维规范。

## C6：budget_consumed 与 settle 同事务

### C6.1 规则

在 **Settle / OrphanSettle 成功事务内**：

```text
budget_consumed_amount += sell_amount  （同一 account 行更新）
```

与 `balance/frozen/ledger/freeze status` 同一 `WithTx`。

失败回滚则 consumed 不增加。

### C6.2 周期切换

独立任务（日/月界）：

```text
若 now 越过 budget_period 边界：
  审计事件记录旧 consumed
  budget_consumed_amount = 0
  更新 period_start/end
```

与在途 settle 并发：靠 account 行锁或 `budget_version`。

### C6.3 告警

仍只读 `consumed/limit` 比例，不进结算事务。

## C7：金额精度与部署约束

### C7.1 金额

- 领域层统一 `decimal`（如 shopspring/decimal）。  
- PG：`NUMERIC(20,8)`（或项目统一精度）。  
- SQLite：**TEXT 存十进制字符串**，禁止 REAL 做余额。  
- JSON 价目入算出的 money 同样走 decimal。

### 7.2 部署

| 条件 | 行为 |
|------|------|
| 多实例 + SQLite | **拒绝启动**或明确 fatal 配置错误 |
| 多实例 + PostgreSQL | 允许；TTL/对账 worker 多副本靠 SQL 条件更新抢占 |
| Redis 关闭 | 功能完整，仅无缓存/提示 |

### 7.3 单测

- 0.1+0.2 类样例必须用 decimal 断言，防止 float 回归。

## 8. 与主路径的集成顺序

```text
数据面：
  Freeze(SQL)
  → Upstream
  → Settle(SQL, C2, C6) 幂等(C1)
  → 失败/崩溃 → TTL(C3 触顶策略) + Orphan Job(C1.4)

控制面：
  Allocate/Liquidate：本地守恒事务 + 幂等
  无改 balance API(C5)

后台：
  Freeze timeout worker
  Orphan reconciler(C1.4)
  Daily reconciliation(C4)
  Budget period rollover(C6.2)
```

## 10. 验收用例（收口专用）

1. 模拟 Settle 前杀进程：TTL 解冻后，作业将 `upstream_success` 补为 `orphan_settled` 或 `orphan_pending`。  
2. 人为 sell > freeze：流水含 extra，余额正确。  
3. 流式跑满 max_total：流停、有结算或挂 pending，无长期 open+无账。  
4. 手工改 ledger 被拒；改 balance 后 R1 告警。  
5. settle 回滚时 budget_consumed 不变；成功则增加。  
6. SQLite 下金额字符串累加无浮点误差；双实例 SQLite 无法启动。

## 11. 小结

| 层级 | 内容 |
|------|------|
| 系统内公式 | 划拨/冻结/结算本地事务守恒（既有设计） |
| 本清单补齐 | 与上游事实对齐、超额、触顶、对账、防篡改、预算一致、精度与部署 |
| 仍依赖运营 | `orphan_pending` 人工补款、R1 异常人工；属可控例外而非静默漏洞 |

按 **C1–C7** 实现后，可将守恒从「库内等式」提升为「可监控、可补偿、可审计的商用闭环」，与当前 PostgreSQL/SQLite 权威账本、Redis 非账本架构一致，并可直接挂入融合架构的 `fund` 包与定时任务框架。
