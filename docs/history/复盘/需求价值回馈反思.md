## 二、已丢失的高价值需求（逐项对标）

### 🔴 第一类：战略级丢失——原始愿景的"预留设计"

#### 1. "对外售卖 Token"的预留设计被彻底删除

**原始讨论**（行 49）：
> "不做发电厂（不卖模型、不对外倒卖 Token（**未来可能会支持，需要预留设计**））"

**v2.0.1 §14：**
> "作为云厂商对外售卖 Token 或模型本身" —— 列入"不在范围"，且**未标注任何预留设计**。

**丢失价值：** 这是产品最重大的商业扩展方向。原始讨论明确要求"预留设计"（架构上支持但不实现），v2.0.1 彻底封死了这条路。如果未来企业需要将内部 AI 能力作为服务对外输出，将从零改造。

---

#### 2. "四级预算层级"被简化为单层

**原始讨论 §2.3.2 + FIN-02：**
> "支持按 **租户 → 一级部门 → 二级部门/项目组 → 成员个人** 设置四级预算上限"
> 
> "构建 `公司总盘(Root Balance)` -> `一级部门` -> `二级部门/项目组` -> `个人余额`"
>
> "每一步调用都会从对应层级余额中**实时扣除**"

**v2.0.1 §5.2：**
> "预算帽挂在 **Account** 上。本定版**不做 Key 级分帽**。"

**丢失价值：** 四级预算体系是原始讨论最核心的财务创新点，对应企业真实的科层制管理。v2.0.1 退化为单一 Account 级预算帽，丧失了：
- 公司总盘 → 部门 → 项目 → 个人的**层级穿透管控**
- "各环节从对应层级实时扣除"的**多级扣费语义**
- 财务上"自上而下划拨、自下而上消费"的完整资金流

---

#### 3. 多模态计价能力丢失

**原始讨论 §2.3.1：**
> "多模态计价：对**图片、音频、视频**等非文本内容，支持按**张数、时长**等维度单独计价。"

**v2.0.1 §4.1 itemCode 基线：** 仅覆盖 Token 维度（prompt_tokens, completion_tokens, prompt_cached_tokens 等），**无图片/音频/视频计价项**。

**丢失价值：** GPT-4o、Gemini 等已经原生支持多模态输入，且上游按图片张数/分辨率计价。v2.0.1 的 itemCode 体系无法表达这些费用项，未来接入多模态模型时计价引擎需要重构。

---

#### 4. 私有化固定摊销模式丢失

**原始讨论 §2.3.1：**
> "私有化固定摊销：对私有化部署的模型，支持按**月/年固定成本**进行摊销，而非按 Token 计量。"

**v2.0.1 §4.2 计价模式：** flat_fee / usage_per_unit / usage_tiered / usage_volume——**四种模式均基于用量**，没有固定摊销模式。

**丢失价值：** 企业部署私有化模型（如 vLLM 推理集群）时，内部结算不应按 Token 计费（因为上游没有 Token 账单），而应按硬件+运维成本摊销。缺少此模式，财务无法对私有化模型做合理的内部成本分摊。

---

#### 5. 缓存折扣计价模式丢失

**原始讨论 §2.3.1：**
> "上下文缓存折扣计价：对复用上下文的 Token 提供**自定义折扣**，降低长对话成本。"

**v2.0.1 §4：** 计价模式中无独立的"缓存折扣"概念。缓存 Token 虽有独立的 itemCode（prompt_cached_tokens），但 cost/sell 双轨中没有折扣率机制。

**丢失价值：** 上游厂商对缓存命中的 Token 通常有 **50%~90% 折扣**。如果企业内部价不能对缓存 Token 做差异化折扣，则部门在使用有缓存优化的模型时无法获得相应激励，降低企业推动缓存优化的动力。

---

### 🟠 第二类：功能级丢失——原始蓝图中的具体能力

#### 6. 轻量级模型预判器（任务复杂度自动路由）

**原始讨论 §2.1.2（MSE-04）：**
> "成本优先智能调度：引入**轻量级模型预判器**。简单任务（翻译、摘要）自动分发至 `gpt-4o-mini` 等低成本模型；复杂推理任务路由至 `GPT-4o / Claude-3.5`。"

**v2.0.1 §3.3 策略矩阵：** 有 S-COST（成本感知），但其语义是"在价格合格集内偏向低价"，**不是**智能任务分类派发。

**丢失价值：** 这是原始讨论中最具体的降本策略——用一个小模型先判断任务复杂度，再将请求路由到对应档位的模型。v2.0.1 的策略矩阵是"同级候选内选便宜的"，缺少"跨级分发"的智能预判能力。这是企业 AI 降本的核心手段之一。

---

#### 7. 自动对账引擎的完整实现逻辑

**原始讨论 FIN-04 + §2.3.3 + 行 453-460：**
> "系统每月初拉取上游供应商账单（**CSV/API**）"
>
> "对账逻辑：供应商应结算总额 vs 网关内部各组织/项目组结算总额。若不一致，系统**高亮差异原因**（如缓存未计费、汇率波动），输出**差异分析报表**供审计"
>
> "月结/日结对账任务 → 拉取上游厂商账单 → 自动对账引擎 → 比对资金池内部总消耗 vs 厂商总账单 → 有差异输出差异分析报告 → **财务修正/冲销**"

**v2.0.1 AUD-03：**
> "对账 | 上游账单与内部 cost 比对；差异分类 | P2"

**丢失价值：** 原始讨论的对账是一个**完整的商业闭环**：拉取 → 逐笔比对 → 差异归类 → 报表输出 → 财务修正。v2.0.1 把它压缩成了不足一行，"财务修正/冲销"环节完全消失。

---

#### 8. 关键性能指标的具体数值

**原始讨论 §3 非功能需求：**
> "支持**万级 QPS**，单请求延迟增加低于 **50ms**"

**原始讨论 §4 表格：**
> "单节点 **5000 QPS**；仅增加 **< 30ms** 业务延迟（基于 Go 技术栈优秀性能）"

**v2.0.1 §12：**
> "附加延迟与吞吐**按硬件在测试计划量化验收**"

**丢失价值：** 具体性能指标是商业合同中的 SLA 基础。没有明确数值，交付验收时各方对"是否达标"会有争议。

---

#### 9. 安全事件报表仪表盘

**原始讨论 §2.2.3：**
> "安全事件报表：提供**外网调用统计、内容拦截排行、违规调度记录**等报表，支持**导出**。"

**v2.0.1：** 有 UI-07 仪表盘（消耗/余额/预算/拦截），但缺少专门的安全事件维度报表，特别是"外网调用统计"和"违规调度记录"。

---

#### 10. 全链路调用追踪 UI

**原始讨论 OPS-03：**
> "支持按 `request_id` 或 `task_id` 或 `user_id` 进行查询，追踪该次调用在网关内的**完整流转链路**（决策路由、安全结果、Token计量、耗时）。"

**v2.0.1 AUD-01：** 有调用审计日志记录，但未承诺一个**可视化全链路追踪界面**，用户需要自行拼接多张日志表。

### 🟡 第三类：价值论证丢失——"为什么"与"价值"被技术表述替代

原始讨论文档有强烈的**叙事性和说服力**，v2.0.1 变成了纯粹的技术规格书。以下高价值论证全部丢失：

| 原始讨论的核心论述 | 在 v2.0.1 中的状态 |
|---|---|
| "Token ≠ 电力：同等数量 Token 在不同模型下价格、业务价值完全不同" | ❌ 深层洞察丢失 |
| "厂商总账单 ≠ 企业内部分户电表" | ❌ 核心矛盾论述丢失 |
| "简单累加式机械统计毫无意义，必须具备业务感知能力" | ❌ 产品哲学丢失 |
| "企业关注点从'模型单价'转向'资源分配、投入产出、Token 使用效率'" | ❌ 行业趋势判断丢失 |
| "普通 API 中转工具：解决'请求能不能送达模型'；企业 AI 网关：解决'AI 能源如何计量、分配、管控、追溯'" | ❌ 差异化定位金句丢失 |
| "这套方案是一台'AI 财务精算机'，而不是一个'API 通道'" | ❌ 商业价值断言丢失 |

| 清算状态机 | ✅ |
| 冻结 + 流式续期 | ✅ |
| 治理 API + 幂等 | ✅ |

### 为什么这样设计（部分丢失 ⚠️）

| 原始设计意图 | v2.0.1 中 |
|---|---|
| "预留对外售卖 Token"→ 预算帽、层级资金池为日后商业化打底 | ❌ 预留设计被删除 |
| "四级预算"→ 对应企业真实的科层制财务管控 | ⚠️ 简化为单层 |
| "轻量级预判器"→ 用 AI 管 AI，自动化降本 | ❌ 策略矩阵无此能力 |
| "多模态计价"→ 为即将到来的多模态爆发做准备 | ❌ itemCode 无法表达 |
| "固定摊销"→ 私有化模型的财务合理性 | ❌ 计价模式缺失 |
| "缓存折扣"→ 激励团队使用缓存优化 | ❌ 折扣机制缺失 |

### 价值在哪（论证丢失 ❌）

v2.0.1 是一份**优秀的技术规格书**，但不是一份有说服力的**产品价值文档**。原始讨论中的四条商业价值断言完全消失：

1. **财务视角的魔法**：让上游供应商账单变成企业内部各组织之间的等价收费闭环账本
2. **安全视角的防线**：在物理逻辑上斩断绕过网关直接调用大模型的可能性
3. **审计视角的护城河**：不可编辑的二进制归档，永久留存的合规硬通货
4. **采购决策锚点**：这不是开源套壳，是能让企业在 T+3 个月内完成 AI 基础设施治理的商业产品

## 五、总结

v2.0.1 在技术规格层面是**严谨自洽**的，但与原始产品讨论相比，存在一条清晰的价值稀释路径：

```
原始讨论（愿景 + 功能 + 价值）
    ↓
v1.0.0（功能 + 规则 + 边界）
    ↓
v1.0.1（+ TokenHub/AxonHub 选型 + 策略矩阵）
    ↓
v1.0.2（+ 预算帽分码修正）
    ↓
v2.0.0（+ ModelGrant + 错误码全表，但压缩第 9 章）
    ↓
v2.0.1（恢复第 9 章 + 门禁/交付物，但原始愿景的"为什么"和"价值"持续淡化）
```

**核心病灶：** 每次迭代都是一次"技术收敛"，但缺少一次"价值回填"——回到最原始的讨论，确认**用户最初要解决的问题、为什么这样设计、价值在哪里**是否仍然被完整覆盖。

建议在 v2.0.2 中完成上述 P0 修复 + 在第 0 章或独立的前言中恢复原始讨论的产品价值叙事。
