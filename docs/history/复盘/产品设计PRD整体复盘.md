# Party 多态模型：复盘与优化方案

## 一、为什么 Party 模型是正确的进化方向

四层固定层级（租户→部门→项目→人）的根本问题是**假设了唯一一种企业形态**。真实世界远非如此：

| 固定层级能表达 | 固定层级无法表达 |
|-------------|----------------|
| 公司 → 部门 → 项目 → 人（树形） | 跨部门战略项目（DAG） |
| 上级划拨下级 | 多方共同出资 |
| 逐级下拨 | 矩阵制（产品线 × 区域） |
| 项目挂在部门下 | 独立项目、外部协作方 |

**Party 多态模型把树变成了图。** org 和 project 是同一层节点，关系边描述结构。这不仅"能应对复杂多变的业务形态"，而且在数学上可以表达**任意企业拓扑**。这个设计决策完全正确。

## 二、在守恒公理下，复盘当前 Party 模型的覆盖度

以 7 条核心公理为约束，逐一检查物理世界场景是否可达：

### 公理回顾

```
A1: 无计量 → 无管理
A2: 无归因 → 无法优化  
A3: 无企业自有调用入口 → 无法真正掌控 AI 资产与成本
A4: 无守恒账本 → 无财务治理护城河
A5: 调度不改账户；价格锚定约束；禁止先调后欠
A6: 四轴正交授权；模型可用范围与资金扣费解耦
A7: 管理员也须经账本服务变更余额
```

### 物理世界场景覆盖度检查

| # | 物理世界场景 | 当前 PRD 覆盖 | 判定 |
|---|-----------|-------------|------|

## 三、三维真缺失分析

### 🔴 缺失 1：Person 作为可预算实体

**物理现实：** 企业最常见的经费管控不是"项目级"或"部门级"，而是**人头费**——"每人每月 ¥500 AI 实验经费"。当前 PRD 明确说"不做 Key 级分帽"，意味着这个场景无法原生支持。

**但这是正确的设计吗？** 有两种路径：

**路径 A（当前）：** Person 不是一个可持有账本的实体。要给人头发钱，必须建一个 Party(project) 然后让人 Key 绑定该 Party 的 Account。

**路径 B（扩展）：** 让 Person 也可以像 Party 一样拥有 Account。这样个人额度就是 Person.Account.budget_cap。

**推荐路径 B，但在模型上要谨慎：**

- Person 和 Party **不是同一层抽象**——Person 是自然人，Party 是组织单元
- 不能让 Person 参与划拨通道（person→person 划拨没有物理意义）
- 但可以让 Person 拥有一个简单的 Account（仅用于预算帽 + 余额不足判断）

**守恒公理约束：** Person.Account 的余额只能来自 Party.Account 的划拨（通过一种新的关系类型，如 `allocates_to`），且必须走完整的流水+幂等。这完全符合 A4（守恒账本）和 A7（管理员也经账本服务）。

**建议：** §2.5 增加 Person Account 设计：

| 对象 | 扩展 |
|------|------|
| Person | **可选**拥有个人 Account（由所属 Party 划拨注入） |
| 个人 Account | 仅支持预算帽 + 消费扣费；**不**支持对外划拨；**不**参与组织间资金通道 |

这比"四级层级"优雅得多：不是固化"部门→人"的树，而是任何 Party 都可以通过 `allocates_to` 边给其成员注入个人经费。

---

### 🔴 缺失 2：组织生命周期（合并/拆分/重组）

**物理现实：** 企业每年都在调整组织架构——部门合并、拆分、重命名、职能转移。当前 PRD 只有"项目清算"状态机，没有"组织变更"语义。

**场景模拟：**

```
Q1: 部门A (余额 ¥80K) + 部门B (余额 ¥50K) 
    → Q2: 合并为 部门C

问题：
- 部门A 和 B 的账本余额如何处理？
- 在途冻结怎么迁移？
- 历史流水归属怎么重映射？
- Key 绑定的 account_id 要不要变？
```

**守恒公理约束：** 所有余额变更必须有流水（A4）。组织的合并/拆分本质上是**特殊的划拨操作**——源账户余额 → 目标账户，且需要在审计中记录组织变更事由。

**建议：** §2.4 增加一种特殊关系边类型 + §8.4 旁边增加组织变更流程：

| 关系类型 | 含义 | 资金处理 |
|----------|------|----------|
| `merged_into` | 组织合并（A 并入 C） | A 清算 → C 接收；历史流水关联 A |
| `split_from` | 组织拆分（C 拆出 B） | C 划拨 N → B；按约定比例 |

组织变更必须：① fund 轴授权；② 强制幂等键；③ 写组织变更审计（before/after 快照）。这与现有清算状态机共享底层机制，不引入新的资金漏洞。

---

### 🟡 缺失 3：模型维度的预算约束

**物理现实：** "GPT-4 预算 ¥50K，所有低价模型共享 ¥10K"——预算不仅按"谁花钱"分，也按"花在哪个模型上"分。

**当前：** 预算帽只在 Account 维度。ModelGrant 控制"能不能用"，但不控制"能用多少"。

**守恒公理约束：** 不违反任何公理——这是在既有预算帽基础上增加一个过滤维度，不改变资金守恒。

**建议：** 这是一个有价值但不紧急的能力。可用两种方式：

- **轻量方案（推荐）：** 在 ModelGrant 上增加可选的 `quota_limit` 字段——deny 之外的第二种限制："允许用，但累计 sell ≤ X"。这本质上是 ModelGrant 的语义扩展，不改变资金层。
- **重量方案：** 独立模型预算表，暂不推荐——违反反膨胀纪律。

建议在 §7.2 ModelGrant 字段中增加：

```
| quota_limit | DECIMAL NULL | 该授权下的消费上限；NULL=不限制；与 Account 预算帽取交集 |
```

---

### 🟡 缺失 4：预算可见性的聚合语义

**物理现实：** 部门负责人需要看到一个仪表盘——"我管的部门 + 下属所有项目的总消耗、总余额、预算使用率"。

**当前：** AUD-04 报表支持多维汇总，但没有显式定义"沿关系边向上聚合"的语义。

**建议：** §9.9 AUD-04 或 §9.10 UI-07 增加一条明确需求：

> "报表支持沿 parent / sponsors 关系边向上聚合：上级 Party 可见所有下级 Party 的汇总消耗与余额（受 data 轴范围约束）"

这不是新功能，是对现有报表能力的语义澄清。

## 四、基于物理世界复盘后的 PRD 优化方案

以下优化全部在已有守恒公理和 Party 模型框架内，**不引入新概念，只补物理世界缺口**：

### 优化 1：§2.5 — Person 可选账本

```diff
  | Person | 实体人 | 通过成员关系进入一个或多个 Party |
+ | Person Account | 可选 | Person 可拥有个人 Account（由所属 Party 通过 allocates 注入）；
+                            仅支持预算帽 + Key 消费扣费；不支持对外划拨 |
```

### 优化 2：§2.4 — 新增关系边类型

```diff
  | owns | 主责/主办 | 不自动产生划拨权 |
  | participates | 协作 | 不自动产生划拨权 |
+ | allocates | 拨入个人 | Party → Person 注入个人经费；仅用于 Person Account |
+ | merged_into | 组织合并 | 源 Party 余额划入目标 Party；走清算类流程 |
+ | split_from | 组织拆分 | 源 Party 按比例划出到新 Party |
```

### 优化 3：§8.4 旁边 — 新增组织变更流程

在清算状态机旁增加：

```
组织合并：active → merging_block_new → merging_drain → merging_transfer → merged
组织拆分：active → splitting → split_completed
```

与清算共享冻结排空机制，复用幂等和流水基础设施。

### 优化 4：§7.2 ModelGrant — 增加额度限制

```diff
  | effect | allow / deny |
+ | quota_limit | DECIMAL NULL | 该授权下累计消费上限（与 Account 预算帽取交集）|
```

### 优化 5：§9.9 — 报表聚合语义

```diff
  | AUD-04 | 报表 | 多维汇总；基础 P0 |
+         规则：支持沿 parent/sponsors 边向上聚合（上级可见下级汇总）；
+         data 轴范围约束生效
```
