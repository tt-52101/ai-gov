# 对审核意见的正式回复（FUN-07 与错误码衔接）

**结论：需要区分。**

「配置比例告警 / 预算上限阻断」与「账户可用余额不足以完成本次冻结」是两类运营语义，必须在错误码与对外文案上分开，否则上层与财务无法区分「花超预算帽」与「账户真没钱」。

| 场景 | 含义 | 对外错误码（约定名） | 典型 HTTP | 说明 |
|------|------|----------------------|-----------|------|
| 预算帽阻断 | 已用（或已用+本次预估）达到/超过该账户或主体配置的**预算上限**（可低于 100% 余额，如 90%） | `BUDGET_CAP_EXCEEDED` | 402 或 403（项目统一即可，须文档固定） | 余额可能仍大于 0，但策略上禁止继续预扣 |
| 余额不足冻结失败 | 可用余额 &lt; 本次所需冻结金额 | `QUOTA_EXHAUSTED` 或 `INSUFFICIENT_BALANCE` | 402 | 物理上冻不起 |
| 无合格路由（价格帽等） | 与钱无关的调度失败 | `NO_ROUTE_WITHIN_PRICE_CAP` 等 | 503/422 | 已有条款 |
| 告警阈值 | 如 80%，**不阻断** | 不作为调用错误码；走通知/事件 | — | 仅告警通道 |

**FUN-07 定版语义：**

- **告警阈值**（如 80%）：只告警，不拒绝调用。  
- **预算上限**：可配置为相对额度上限（金额或占初始/分配额度的百分比等，由配置模型表达）；**允许低于「当前余额 100%」**，形成软预算帽。命中则**阻断新预扣**，返回 `BUDGET_CAP_EXCEEDED`。  
- **余额不足**：冻结时可用余额不够，返回 `INSUFFICIENT_BALANCE`（或 `QUOTA_EXHAUSTED`，全项目唯一命名，下文统一为 `INSUFFICIENT_BALANCE`）。  

两者判定顺序建议：先做预算帽校验（若已配置），再做冻结金额与可用余额比较，避免语义混淆。

以下条款已写入定版 PRD 正文（FUN-07、6.1、6.5），可签发。

### 0.2 设计哲学

Token 是 AI 时代的电力。本产品不运营模型供给、不对外倒卖 Token，只在企业内部提供：

- 统一模型调用入口  
- 精确计量与双轨计价  
- 主体经费账本、划拨与清算  
- 安全控制与不可抵赖审计  

**目标闭环：**

> 模型接入 → 安全拦截 → 智能调度 → 实时扣费 → 资金回笼与清算 → 对账审计。

### 0.3 核心公理（不可配置取消）

1. **无计量则无管理。**  
2. **无归因则无法优化。**  
3. **无企业自有调用入口则无法真正掌控 AI 资产与成本。**  
4. **无守恒账本则无财务治理护城河。**  
5. **调度不得改变扣费账户；内部结算价格受请求锚定与上浮上限约束；禁止先调用后欠费。**  
6. **数据范围、资金、身份密钥、调度配置四轴正交授权，禁止一轴推导另一轴特权。**  
7. **平台管理员也必须经账本服务与流水变更余额，不得提供绕过守恒的后门接口。**

### 0.4 能力优先级（核心竞争力顺序）

| 优先级 | 能力域 | 说明 |
|--------|--------|------|
| **P0** | 统一接入与密钥托管 | 消灭野连接，全部调用经网关 |

| **P0** | 正交授权与数据不越权 | 四轴授权、范围过滤、防 IDOR |

## 1. 产品综述

### 1.1 要解决的问题

1. 员工与团队私自采购上游 API Key，调用黑箱，无法统一禁用与审计。  
2. 财务只能拿到厂商总账单，无法按组织、项目、人员、应用做内部结算与利润分析。  
3. 成本失控：无预算预扣、无实时阻断、无内部结算价与上游成本的双轨可见性；预算帽与「真没钱」混淆导致运营抓手不足。  
4. 合规风险：敏感数据可能经未审批路径出境；管理员改配置缺少不可篡改留痕。  
5. 可用性与成本难以兼顾：仅写死「主→备→降级→缓存」四层不足以支撑商业灵活组合；调度若不受内部价格约束会击穿账本。

### 1.2 价值主张

| 主张 | 说明 |
|------|------|
| 统一治理 | 全部模型调用经单一企业网关，消灭野连接 |
| 财务闭环 | 主动预算、预扣与实扣、主体间划拨与清算、双轨计量、预算帽与余额不足可区分、对账 |
| 安全合规 | 密钥托管、出网策略、内容安全、全链路与配置变更审计 |
| 降本增效 | 在准确计量与价格约束前提下，按可插拔策略矩阵做成本、健康、权重、亲和等调度 |

### 1.3 产品边界

**本产品负责：**

- 身份、成员、主体（组织与项目等）、正交授权  
- 上游模型与私有化资源接入、上游密钥托管  
- 调用接入（OpenAI 兼容等）、安全拦截扩展点、路由调度  
- Token 计量、双轨计价、账本、划拨、预扣结算、清算、预算告警与预算帽  
- 调用审计、配置变更审计、对账与成本报表  
- 管理控制台与对等的控制面治理 API  
- 运维可观测  

**本产品不负责：**

- Agent / 工作流编排、Skill 市场、面向终端用户的业务对话产品 UI  
- 作为云厂商对外售卖 Token 或模型本身  
- 同一请求拆分到多个账本分摊扣费  
- 默认透支信用（负余额作为正常成功路径）  
- 由业务客户端负责冻结续期  
- 以公链/联盟链作为热路径余额系统记录  

与上层系统的契约：提供 **OpenAI 兼容 HTTP API**（及必要的其它协议兼容面）；支持请求携带业务标签（如 `user_id`、`task_id`、`agent_id`、`skill_id` 等）用于归因。业务标签不替代鉴权，不替代扣费账户。

## 2. 物理世界模型与多态约束

### 2.1 设计出发点

真实企业中 AI 经费与编制形态是多态的。系统不得假设唯一结构「公司 → 部门 → 项目 → 人」，也不得强制「项目必须挂在某个部门下」。

### 2.2 典型物理场景

| 场景 | 组织 | 项目 | 关系与资金 |
|------|------|------|------------|
| 部门日常额度 | 有常设部门 | 可不建项目 | 部门主体直接持有账本，人的 Key 扣部门账本 |
| 部门主责专项 | 有 | 有 | 可用「主责」关系关联；项目可自有账本 |
| 公司级战略项目 | 多个事业部 | 有，可与部门平级 | 多部门出资到同一项目账本；项目有独立 Leader |
| 跨主体协作 | 内外部组织 | 有 | 人可只加入项目、不加入内部部门 |
| 矩阵制 | 产品线、区域等 | 有 | 多协作关系；一次调用只扣一个账本 |
| 结项还钱 | — | 结束 | 剩余资金回流；Key 失效或改绑 |

### 2.3 统一主体：Party

组织（org）与项目（project）是同一层语义上的**主体（Party）**，均可：持有账本、拥有成员、指定 Leader、作为授权资源。

- 不强制项目从属于某个组织。  
- 需要结构时用显式关系边描述。  
- 控制台可分「组织」「项目」导航，底层模型与权限引擎必须统一。

### 2.4 关系边

| 关系类型 | 含义 | 与资金的关系 |
|----------|------|----------------|
| parent | 组织汇报树 | 默认允许上级 → 下级划拨 |
| sponsors | 出资 | 默认允许出资方 → 被出资方划拨 |
| owns | 主责 / 主办 | 不自动产生划拨权 |
| participates | 协作 | 不自动产生划拨权 |

### 2.5 人、Key、账本与消费定理

| 对象 | 物理对应 | 规则 |
|------|----------|------|
| Person | 实体人 | 通过成员关系进入一个或多个 Party |
| API Key | 消费凭证 | 必须绑定且仅绑定一个 `account_id`；调用与扣费的唯一入口 |
| Account | 小金库 | 归属某个 Party；可用余额与冻结金额 |
| Leader | 负责人 | 对本 Party 默认责任角色；权限以显式授权为准 |

**资金流转强制规则：**

1. 划拨：一方减少、另一方增加，金额相等，同一事务。  
2. 预扣：可用余额转入冻结，必须带冻结标识与过期时间；预扣前可经预算帽校验。  
3. 结算：按实际内部价从冻结结清，多退少补。  
4. 清算：按状态机阻断新调用、排空冻结后回流资金并收口 Key。  
5. 任何余额变更必须有流水；禁止无流水改账；默认不允许成功路径产生负余额。  
6. 关键资金写操作必须支持幂等。

**消费强制规则：** 内部结算金额（sell）只从 Key 绑定账户扣除，并归因到 Key 所属实体人；业务标签只做报表归因，不形成第二套资金。

### 2.6 可迭代与扩展原则

稳定核心上述语义；扩展走策略插件、价目 JSON、边类型、安全钩子；热字段原子；复杂进 JSON；禁止表与横向字段无限膨胀。

## 6. 关键边界规则与流程

### 6.1 预扣、预算帽、价格约束与结算

1. 计算 \(P_{request}\)（请求锚定内部 sell 预估）。  
2. 候选价格约束：\(P_{candidate} \le P_{request}(1+\delta)\)；**默认 δ=0**；**硬上限 20%**；改 δ 必须关键配置审计；不合格剔除；集合为空 → `NO_ROUTE_WITHIN_PRICE_CAP`，无上游调用。  
3. **预算帽校验（若已配置）：** 若已用额度（或已用+本次预估，以详细设计选定的口径为准并在实现中固定）达到/超过预算上限 → **拒绝预扣**，返回 **`BUDGET_CAP_EXCEEDED`**。  
4. 冻结额 = 合格候选预估 sell 的最大值；可用余额不足 → **`INSUFFICIENT_BALANCE`**，不发起上游调用。  
5. 调度仅在合格集上执行；**account_id 锁定**。  
6. 实扣 sell、记 cost；多退少补；冻结失效走补偿流水+告警。

**判定顺序（预扣阶段）：** 价格合格集 →（可选）预算帽 → 可用余额与冻结额比较 → 写入冻结。

### 6.2 划拨路径

默认：parent 仅向下；sponsors 仅出资方→被出资方；owns/participates 不开通；无关系禁止除非白名单+fund。清算回流显式目标+授权+审计。

### 6.3 冻结与流式续期

默认 TTL 15 分钟（可配上下限）。流式由**网关**自动续期同一 freeze_id（不增金额）；累计上限可配；客户端不负责续期。超时后台解冻留流水。

### 6.4 清算状态机

`active` → `liquidating_block_new` → `liquidating_drain` → `liquidating_transfer` → `liquidated`。有未到期冻结不得划走占用额。

### 6.5 调用主路径与错误码区分

**主路径：**

1. Key 鉴权与账户绑定校验。  
2. 安全钩子（若启用）。  
3. \(P_{request}\) → 候选与价格过滤。  
4. 预算帽（若配置）→ 冻结。  
5. 策略矩阵选路 → 托管密钥调用上游。  
6. 流式续期 → 规范化用量 → 双轨结算 → 审计。  
7. 返回兼容响应。

**调用方可见错误语义（须区分，名称全项目统一）：**

| 错误码 | 含义 | 调用是否达上游 |
|--------|------|----------------|
| `BUDGET_CAP_EXCEEDED` | 命中配置的预算上限（可为软帽，余额未必为 0） | 否 |
| `INSUFFICIENT_BALANCE` | 可用余额不足以完成本次冻结 | 否 |
| `NO_ROUTE_WITHIN_PRICE_CAP` | 无价格合格候选 | 否 |
| `AUTH_FAILED` / Key 无效或人已禁用 | 鉴权失败 | 否 |
| `COMPLIANCE_BLOCKED` | 出网/内容等合规拦截 | 否 |
| 上游故障类 | 渠道错误、超时等 | 视重试策略 |

HTTP 状态码在详细设计中与上表一一固定（建议预算帽与余额不足均用 402 或均用 403，但**body 内错误码必须不同**）。告警比例（如 80%）**不**产生调用错误码，仅事件/通知。

### 6.6 划拨路径

fund 授权 → 通道校验 → 幂等键 → 事务双边记账 → 审计。

### 6.7 治理 API 幂等

划拨、清算等资金写：Idempotency-Key；同键同指纹重放；异指纹拒绝；窗口建议 ≥24h。

### 6.8 账本技术

热账本 = ACID SQL + 只追加流水；不用区块链做热账本；可选哈希归档增强。
