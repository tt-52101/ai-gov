## 0. 文档说明与设计哲学

### 0.1 文档性质

本文档是独立、完整、详细的产品需求规格。所有核心需求、边界约束、物理世界模型、功能矩阵、流程规则、数据纪律、非功能指标、验收标准与分期交付均在正文中写明，不依赖其它会话或外部文稿补全语义。

### 0.2 设计哲学

Token 是 AI 时代的电力。本产品不运营模型供给、不对外倒卖 Token，只在企业内部提供：

- 统一模型调用入口  
- 精确计量与双轨计价  
- 主体经费账本、划拨与清算  
- 安全控制与不可抵赖审计  

**目标闭环：**

> 模型接入 → 安全拦截 → 智能调度 → 实时扣费 → 资金回笼与清算 → 对账审计。

### 0.3 核心公理（不可配置取消）

1. **无计量则无管理。**  
2. **无归因则无法优化。**  
3. **无企业自有调用入口则无法真正掌控 AI 资产与成本。**  
4. **无守恒账本则无财务治理护城河。**  
5. **调度不得改变扣费账户；内部结算价格受请求锚定与上浮上限约束；禁止先调用后欠费。**  
6. **数据范围、资金、身份密钥、调度配置四轴正交授权，禁止一轴推导另一轴特权。**  
7. **平台管理员也必须经账本服务与流水变更余额，不得提供绕过守恒的后门接口。**

### 0.4 能力优先级（核心竞争力顺序）

| 优先级 | 能力域 | 说明 |
|--------|--------|------|
| **P0** | 统一接入与密钥托管 | 消灭野连接，全部调用经网关 |
| **P0** | **财务治理与计量闭环** | 双轨计价、主体账本、划拨清算、Key 扣费、守恒流水——**第一护城河** |
| **P0** | 正交授权与数据不越权 | 四轴授权、范围过滤、防 IDOR |
| **P0** | 调度与资金强制边界 | 价格帽、账户锁定、禁止先调后欠费 |
| **P0** | 治理 API 与资金写幂等 | 与控制台对等，防重复记账 |
| **P1** | **可插拔路由策略矩阵与降本高可用** | 单策略启停、混合组合，非固化四层 |
| **P1** | 基础运营报表与仪表盘 | 消耗、余额、拦截可见 |
| **P2** | 内容安全与出网强化 | 具体扫描引擎可后置 |
| **P2** | 配置变更快照强化、上游账单自动对账 | 等保与运营深化 |

**说明：** 内容安全、出网等具体能力可为 P2，但数据面主路径必须在财务闭环阶段预留**安全扩展点（架构级 P0）**，避免后期全链路改造。若合同强制合规，该交付项目可将对应安全能力提升为项目级 P0。

## 1. 产品综述

### 1.1 要解决的问题

企业规模化使用大模型时普遍出现：

1. 员工与团队私自采购上游 API Key，调用黑箱，无法统一禁用与审计。  
2. 财务只能拿到厂商总账单，无法按组织、项目、人员、应用做内部结算与利润分析。  
3. 成本失控：无预算预扣、无实时阻断、无内部结算价与上游成本的双轨可见性。  
4. 合规风险：敏感数据可能经未审批路径出境；管理员改配置缺少不可篡改留痕。  
5. 可用性与成本难以兼顾：多模型多渠道若只写死“主→备→降级→缓存”四层，无法支撑商业级灵活组合；若调度不受内部价格约束，会击穿账本。

### 1.2 价值主张

| 主张 | 说明 |
|------|------|
| 统一治理 | 全部模型调用经单一企业网关，消灭野连接 |
| 财务闭环 | 主动预算、预扣与实扣、主体间划拨与清算、双轨计量、对账 |
| 安全合规 | 密钥托管、出网策略、内容安全、全链路与配置变更审计 |
| 降本增效 | 在准确计量与价格约束前提下，按可插拔策略矩阵做成本、健康、权重、亲和等调度 |

### 1.3 产品边界

**本产品负责：**

- 身份、成员、主体（组织与项目等）、正交授权  
- 上游模型与私有化资源接入、上游密钥托管  
- 调用接入（OpenAI 兼容等）、安全拦截扩展点、路由调度  
- Token 计量、双轨计价、账本、划拨、预扣结算、清算  
- 调用审计、配置变更审计、对账与成本报表  
- 管理控制台与**对等的控制面治理 API**  
- 运维可观测  

**本产品不负责：**

- Agent / 工作流编排、Skill 市场、面向终端用户的业务对话产品 UI  
- 作为云厂商对外售卖 Token 或模型本身  
- 同一请求拆分到多个账本分摊扣费  
- 默认透支信用（负余额作为正常成功路径）  
- 由业务客户端负责冻结续期  
- 以公链/联盟链作为热路径余额系统记录  

与上层系统的契约：提供 **OpenAI 兼容 HTTP API**（及必要的 Anthropic 等兼容面）；支持请求携带业务标签（如 `user_id`、`task_id`、`agent_id`、`skill_id` 等）用于归因。业务标签**不替代**鉴权，**不替代**扣费账户。

### 1.4 目标用户

| 角色 | 主要诉求 |
|------|----------|
| 平台管理员 / 架构师 | 部署、资源池、路由档案、系统配置、上游密钥 |
| 财务 / 成本控制 | 账本、划拨、内部加价、报表、对账、清算 |
| 安全 / 合规 | 出网、拦截、审计检索、保留策略 |
| 组织或项目负责人（Leader） | 本主体经费、成员与 Key、消耗可见 |
| 实体人（员工/外包） | 持有 Key、合法调用、查看本人用量 |

## 2. 物理世界模型与多态约束

### 2.1 设计出发点

真实企业中，AI 经费与编制形态是**多态**的。系统不得假设唯一结构「公司 → 部门 → 项目 → 人」，也不得强制「项目必须挂在某个部门下」。

### 2.2 典型物理场景

| 场景 | 组织 | 项目 | 关系与资金 |
|------|------|------|------------|
| 部门日常额度 | 有常设部门 | 可不建项目 | 部门主体直接持有账本，人的 Key 扣部门账本 |
| 部门主责专项 | 有 | 有 | 可用「主责」关系关联；项目可自有账本 |
| 公司级战略项目 | 多个事业部 | 有，可与部门平级 | 多部门出资到同一项目账本；项目有独立 Leader |
| 跨主体协作 | 内外部组织 | 有 | 人可只加入项目、不加入内部部门 |
| 矩阵制 | 产品线、区域等 | 有 | 多协作关系；**一次调用只扣一个账本** |
| 结项还钱 | — | 结束 | 剩余资金回流出资方或指定账户；Key 失效或改绑 |

### 2.3 统一主体：Party

**组织（org）与项目（project）是同一层语义上的「主体（Party）」**，都能：持有账本、拥有成员、指定 Leader、作为授权资源。

- **不强制**项目从属于某个组织。  
- 需要结构时，用**显式关系边**描述，而不是类型继承。  
- 控制台可以分「组织」「项目」两套导航，底层模型与权限引擎必须统一，避免两套账本、两套授权。

### 2.4 关系边（可选、可多）

| 关系类型 | 含义 | 与资金的关系 |
|----------|------|----------------|
| parent | 组织汇报树上下级 | 默认允许**上级 → 下级**划拨 |
| sponsors | 出资 | 默认允许**出资方 → 被出资方**划拨 |
| owns | 主责 / 主办 | **不**自动产生划拨权 |
| participates | 协作 | **不**自动产生划拨权 |

无关系时：独立项目或独立组织费用池均可成立。

### 2.5 人、Key、账本与消费定理

| 对象 | 物理对应 | 规则 |
|------|----------|------|
| Person | 实体人 | 通过成员关系进入一个或多个 Party |
| API Key | 消费凭证（工卡） | 必须绑定且仅绑定一个 `account_id`；调用与扣费的唯一入口 |
| Account | 小金库 | 归属某个 Party；记录可用余额与冻结金额 |
| Leader | 负责人 | 对本 Party 资金与成员等事项的默认责任角色；权限仍以显式授权为准，避免仅靠头衔暗含万能权限 |

**资金流转强制规则：**

1. 划拨：一方减少、另一方增加，金额相等，同一事务。  
2. 预扣：可用余额转入冻结，必须带冻结标识与过期时间。  
3. 结算：按实际内部价从冻结结清，多退少补。  
4. 清算：按状态机阻断新调用、排空冻结后，再回流资金并收口 Key。  
5. 任何余额变更必须有流水；禁止无流水改账；默认不允许成功路径产生负余额。  
6. 关键资金写操作必须支持幂等，避免网络重试导致重复记账。

**消费强制规则：**

- 最终内部结算金额（sell）只从 **Key 绑定的账户**扣除，并归因到 **Key 所属实体人**。  
- 业务标签（project/dept/agent/task 等）只做报表归因，**不形成第二套资金**。  
- 禁止「只扣项目、不记到人」的设计。

### 2.6 可迭代与扩展原则

- **稳定核心：** 计量、双轨、账本守恒、Key 扣费、四轴授权、统一入口、调度价格上限与账户锁定、冻结生命周期、清算状态机、治理 API 幂等。  
- **扩展面：** 新关系类型、新费用项编码、新路由策略插件、价目分时规则、安全钩子、对账连接器、划拨白名单。  
- **存储纪律：** 热字段原子精简；复杂结构放入 JSON；禁止为每个扩展点无限加表加列。  
- **发布演进：** 可先「只计量双轨、不实扣」再「实扣」；策略可 shadow 观察后再生效。

## 3. 开源底座选型与能力融合

### 3.1 两套开源系统功能矩阵对比

| 维度 | TokenHub（astaxie/TokenHub） | AxonHub（looplj/axonhub） |
|------|------------------------------|---------------------------|
| 定位 | 企业私有 AI 网关：统一入口、项目 Key、路由、配额、用量归因、RBAC、审计 | 通用 AI 网关：多协议、强 Trace、细粒度成本、自适应负载 |
| 技术栈 | Go 后端 + 管理台；SQLite/PostgreSQL；OpenAI 兼容 | 多协议适配；渠道×模型价目；成本明细 |
| 组织/项目 | 项目空间、成员、项目 Key、成本归因 | 相对偏通道与调用侧 |
| 路由 | 优先级、权重、失败回退、亲和、健康诊断 | 多维评分、故障转移、负载 |
| 计费 | 基础用量与成本管控 | **itemCode 级明细、flat_fee / usage_per_unit / usage_tiered、缓存分项、JSON 价目** |
| 私有化 | 明确 SQLite-first + PG 多实例 | 开源可私有化 |
| 与本 PRD 缺口 | 缺双轨结算、守恒账本、划拨清算、正交四轴、价格帽 | 缺企业内资金闭环与 Party 账本 |

### 3.2 选型结论

- **主仓库底座：TokenHub**——项目治理、Key、路由骨架、审计、私有化部署更贴近「治理底座」，**最小化二次开发路径更短**。  
- **必须吸收 AxonHub 的：**  
  - 费用项编码与计算口径（含缓存读写拆分、避免输入与缓存重复计价）  
  - 三种（及以上）计价模式  
  - 渠道×模型 JSON 价目（含分时 schedule 思路）  
  - 请求级 costItems 明细  
  - 多维负载/健康评分思想（纳入策略矩阵实现，而非替换整仓）  

本产品在 AxonHub 单轨成本之上强制增加 **cost（上游成本）/ sell（内部结算价）双轨**。

### 3.3 路由：从固化四层到可插拔策略矩阵

产品早期若只规定「主模型 → 备用 → 降级 → 缓存」四层，**不足以**支撑商业高可用与灵活运营。定版要求：

- 策略**可注册**  
- 对某一调度档案可**单独启用或禁用**  
- 可**混合组合**（加权评分模式或优先级链模式）  
- 「四层降级」仅作为**一种档案预设**，不是唯一实现  

**基线策略矩阵（必须可插拔）：**

| 策略代码 | 名称 | 作用 | 是否允许禁用 |
|----------|------|------|----------------|
| S-PRI | 优先级分组 | 主备硬分组与顺序 | 可 |
| S-HEALTH | 健康与熔断 | 失败率、连续失败、冷却、半开 | 可 |
| S-WEIGHT | 权重与负载 | 按权重与历史负载分配 | 可 |
| S-AFFINITY | 会话亲和 | 同会话优先同一渠道（利于缓存与连贯） | 可 |
| S-COST | 成本感知 | 在价格合格集内偏向更低 sell 或 cost | 可 |
| S-LATENCY | 延迟感知 | 根据 TTFT 或端到端延迟倾向 | 可 |
| S-ERROR | 错误率感知 | 近期成功率惩罚 | 可 |
| S-RATE | 限流感知 | 降低触达 RPM/TPM/429 热点的概率 | 可 |
| S-TAG | 业务标签 | 按请求 Tag 定向或加权（可选） | 可 |
| S-COMPLIANCE | 合规网络 | INTERNAL_ONLY 等硬过滤 | **硬策略，不可对合规主体关闭** |
| S-CACHE | 缓存/兜底 | 最后手段的降级渠道 | 可 |

**档案示例（可配置，非写死代码）：**

- `simple-failover`：接近传统四层（PRI + HEALTH + 有限 WEIGHT）  
- `ha-cost`：PRI + HEALTH + WEIGHT + COST + AFFINITY  
- `compliance-strict`：S-COMPLIANCE 强制 + PRI + HEALTH  

所有档案在跑策略前必须先经过**价格合格集过滤**（见第 6 章）；调度结果**不得修改** `account_id`。

## 4. 系统架构

### 4.1 逻辑分层

```text
上层应用 / Agent
       │  OpenAI 兼容 API + 业务标签
       ▼
接入层：Key 鉴权 → 身份与有效性 → 内容安全钩子 → 出网策略钩子
       ▼
资金层：解析账户 → 请求锚定内部价 → 候选价格过滤 → 冻结（TTL / 流式网关续期）
       ▼
调度层：策略引擎（可插拔矩阵）选择渠道/模型 → 上游调用（托管密钥）
       ▼
计量层：规范化用量 → 计算 cost 与 sell → 结算 → 写审计日志
       ▼
控制面：Party、成员、授权、划拨清算、价目、路由档案、密钥仓库、对账、报表
       │
       └── 治理 API 与管理控制台（同一鉴权模型；资金写操作幂等）
```

### 4.2 平面划分

| 平面 | 职责 |
|------|------|
| 数据面 | 鉴权、预扣、调度、转发、结算、调用日志、冻结续期 |
| 控制面 | 配置、主体、资金操作、授权、价目、路由、密钥、审计查询 |
| 运维面 | 健康、指标、探针、备份、多实例协调、冻结超时任务 |

### 4.3 架构原则

1. 厂商中立，规则与数据归属企业。  
2. 治理优先，转发为辅。  
3. 调用数据必须能翻译成财务可理解的成本与结算信息。  
4. 私有化优先，支持内网与国产化运行环境。  
5. 核心路径短；扩展通过策略插件与配置，不破坏扣费与授权语义。  
6. 热账本采用 **ACID 关系库**（PostgreSQL / TiDB / OceanBase 等），**不以区块链/联盟链作为余额系统记录**。

### 4.4 技术方向（推荐）

| 层次 | 推荐 |
|------|------|
| 网关与控制面后端 | Go（与 TokenHub 一致） |
| 账本与事务数据 | PostgreSQL / TiDB / OceanBase |
| 限流与短状态 | Redis（可选） |
| 异步任务 | 可选消息队列（对账、超时解冻等） |
| 日志检索 | Elasticsearch 或企业内等效 |
| 监控 | Prometheus + Grafana |
| 部署 | Docker / Kubernetes；离线/内网安装包；国产 CPU/OS 在阶段 A 验证 |

## 5. 功能需求详述

### 5.1 统一接入与模型资源池

| 编号 | 名称 | 描述与规则 | 优先级 |
|------|------|------------|--------|
| RES-01 | 多上游接入 | 支持主流公有云与国内模型 API，以及 OpenAI 兼容的私有化部署（如 vLLM、Ollama、KServe 等）。以适配器方式扩展新上游。 | P0 |
| RES-02 | 上游密钥仓库 | 上游密钥仅保存在网关侧，加密存储；调用方只持有企业下发的网关 Key。创建/轮换经控制面；完整明文不落日志、不二次回显。 | P0 |
| RES-03 | 密钥权限 | 仅具备 **routing** 轴「上游密钥写」权限的角色可录入、更新、废弃密钥；fund/data/iam 默认不可访问。 | P0 |
| RES-04 | 健康与状态 | 对渠道/资源做健康探测，区分可用、降级、不可用；支撑调度避让。 | P0 |
| RES-05 | 资源标签 | 支持成本、区域、是否内网等标签，供策略与合规使用。 | P1 |
| RES-06 | 兼容 API | 提供 Chat Completions 等 OpenAI 兼容接口；按需提供 Messages 等其它协议兼容。 | P0 |
| RES-07 | 请求标识 | 全链路 `request_id`；透传并记录业务标签。 | P0 |

### 5.2 双轨计价与用量计量

计价必须贴近真实上游账单结构，**禁止**用粗糙的「模型能力多维度档位」替代 Token 类型明细。必须按开源系统（AxonHub）已验证的费用项与模式吸收融合。

**费用项（itemCode）基线（可扩展）：**

| itemCode | 含义 |
|----------|------|
| prompt_tokens | 输入（须与缓存类拆分，避免重复计价） |
| completion_tokens | 输出 |
| prompt_cached_tokens | 缓存读 |
| prompt_write_cached_tokens | 缓存写 |
| completion_reasoning_tokens | 推理类输出（若上游提供） |
| 厂商特定缓存 TTL 变体等 | 按扩展项增加，不改整体结构 |

**计价模式：**

| 模式 | 说明 |
|------|------|
| flat_fee | 按次固定费用 |
| usage_per_unit | 按单位用量（通常为每 1M Token） |
| usage_tiered | 阶梯价格（分段累计） |
| usage_volume（可选） | 按总量落档后整单同一单价（若吸收） |

**双轨：**

| 轨道 | 含义 | 用途 |
|------|------|------|
| cost | 上游成本（应付） | 对账、毛利分析 |

价目挂载在 **渠道 × 模型** 维度；一条价目以结构化文档（JSON）保存各 item 的 cost/sell、模式、阶梯与可选分时覆盖规则（schedule），**避免为分时、阶梯各建一套表**。

| PRI-01 | 价目配置 | 管理端维护渠道模型价目；支持双轨；变更需审计。 | P0 |
| PRI-02 | 用量解析 | 从上游响应规范化解析各 token 类型；缓存与输入不重复计费。 | P0 |
| PRI-03 | 费用计算 | 按价目与用量输出 cost 总额、sell 总额及分项明细（costItems）。 | P0 |
| PRI-04 | 落账字段 | 调用记录保存 cost、sell、分项明细、账户、人、Key、主体与业务标签。 | P0 |

## 6. 关键边界规则与流程（完整强制条款）

### 6.1 预扣、调度价格约束与结算

**目标：** 避免调度落到更贵内部价时「调用已发生、冻结不足」。

1. **请求锚定内部价 \(P_{request}\)**  
   由请求中的逻辑模型（及渠道价目）、预估用量确定内部 sell 预估基准金额。

2. **候选价格约束**  
   - 调度候选须满足：\(P_{candidate} \le P_{request} \times (1 + \delta)\)。  
   - **默认 \(\delta = 0\)**（不得超过锚定 sell）。  
   - 仅当调度档案显式配置上浮时允许 \(\delta > 0\)。  
   - **\(\delta\) 配置硬上限为 20%**；超过上限的配置**拒绝保存**。  
   - **\(\delta\) 的任何修改必须记为关键配置变更审计**（操作者、档案 ID、前后值、时间），不可仅写普通操作日志。  
   - 不满足约束的候选：**直接剔除**；若无合格候选 → 返回明确错误（如 `NO_ROUTE_WITHIN_PRICE_CAP`），**不得发起上游调用**，**不得**先调用再欠费。

3. **冻结金额**  
   在价格过滤后的候选集上，取「预估 sell」的**最大值**作为冻结金额（候选为空则不冻结、直接拒绝）。

4. **结算**  
   按实际用量与实际落地价目计算 sell 与 cost；从对应冻结结清；多退少补。  
   若冻结已过期或不存在：不得对账户做无冻结依据的扣减；若调用已成功，记补偿结算流水并告警，进入人工复核，禁止静默丢账。

5. **账户锁定**  
   全流程扣费账户 = 鉴权时 Key 绑定的账户，调度不得修改。

### 6.2 划拨路径规则

| 路径 | 默认是否允许 | 方向 |
|------|--------------|------|
| parent（组织树） | 是 | 仅上级 → 下级 |
| sponsors（出资） | 是 | 仅出资方 → 被出资方 |
| owns / participates | 否 | 不自动开通划拨 |
| 无关系双方 | 否 | 除非划拨白名单 + fund 授权 |

- 平级任意互转：默认禁止。  
- 清算回流：在清算操作中显式指定目标账户（通常为上级或原出资方），须 fund 授权与审计。  
- 系统提供资金通道配置；默认即上表，可收紧；放宽必须显式配置。

### 6.3 冻结生命周期与流式续期

1. 每笔冻结包含：`freeze_id`、账户、金额、`expires_at`、关联 request_id（若有）。  
2. **默认初始 TTL：15 分钟**（可配置，须有上下限，例如单次窗口 1–60 分钟）。  
3. **续期责任在网关侧，不在业务客户端。**  
   - 非流式：一次请求在 TTL 内完成；超时由后台解冻。  
   - **流式（请求声明 stream=true 或等价）：** 网关在流式响应仍在进行时，**自动续期**同一 `freeze_id` 的 `expires_at`（例如按上游有效数据或固定心跳间隔延长一个续期步长）。  
   - 续期**不得增加冻结金额**，仅延长有效期。  
   - 单次调用冻结有效期累计上限可配置（例如不超过 2 小时）；达到上限则结束续期，行为须可观测。  
4. 后台任务扫描过期冻结：自动解冻，流水类型标识为超时解冻。  
5. 真相以持久化记录为准，不依赖单机内存。

### 6.4 清算状态机

```text
active
  → liquidating_block_new     // 拒绝新调用与新冻结；在途请求可继续
  → liquidating_drain         // 等待活跃冻结 = 0 或全部过期解冻
  → liquidating_transfer      // 余额转入目标账户
  → liquidated                // Key 吊销或解绑；主体只读
```

- 存在未到期冻结时，**不得**把冻结占用的金额当作可划转余额转走。  
- 可配置最长等待；超时仍有冻结 → 告警并保持 drain，不自动强行负账。  
- 流式在途默认允许跑完或直至冻结规则终止；除非安全策略要求强制中断。

### 6.5 调用主路径

1. 客户端使用网关 Key 调用兼容 API。  
2. 校验 Key 有效、归属人未禁用、已绑定账户。  
3. 执行网络与内容策略钩子（若启用）。  
4. 计算 \(P_{request}\)；调度生成候选并做价格过滤；按最大合格预估冻结；不足则拒绝。  
5. 在合格候选中按策略矩阵选择渠道与模型；使用托管上游凭证调用。  
6. 流式场景由网关维持冻结续期直至结束或触达累计上限。  
7. 规范化用量；计算 cost、sell；结算；写调用审计。  
8. 返回上游兼容响应；错误码区分鉴权失败、额度不足、无合格路由、合规拦截、上游故障等。

### 6.6 划拨路径

1. fund 授权校验。  
2. 通道规则校验。  
3. 幂等键校验。  
4. 事务内双边记账与流水。  
5. 操作审计。

### 6.7 治理 API 幂等

| 项 | 规则 |
|----|------|
| 适用范围 | 至少包括：划拨、清算、冻结相关补偿、以及其它会导致余额或主体资金状态变化的写接口 |
| 机制 | 客户端提供 **Idempotency-Key**；服务端对「键 + 操作者 + 接口范围」在有效窗口内去重 |
| 行为 | 重复请求返回首次成功结果（或明确的「已处理」语义），**不得**第二次记账 |
| 同键异参 | 请求指纹不一致则拒绝，防止误用 |
| 存储 | 幂等记录保留合理窗口（建议不少于 24 小时） |
| 审计 | 流水或审计中可关联 idempotency_key |

只读接口不强制幂等键。

### 6.8 账本技术选型约束

- **系统记录：** PostgreSQL / TiDB / OceanBase 等强事务库；`accounts` + 只追加 `ledgers`。  
- **不采用**公链、联盟链、QLDB 等作为热路径余额与划拨主账本（单企业权威、毫秒级预扣、复杂报表与私有化要求不匹配）。  
- **可选增强：** 流水禁止业务 UPDATE/DELETE；定期哈希摘要归档至 WORM 存储，用于审计增强，不替换热账本。

## 7. 数据模型原则（反膨胀）

### 7.1 逻辑实体

Party、PartyEdge、Account、Ledger、Freeze、Person、Membership、Grant、ApiKey、ModelPrice、渠道与模型资源、调用与用量日志、审计日志、幂等记录、划拨白名单（可选配置）。

### 7.2 表与字段纪律

- **新增逻辑表严格控制数量**，优先：parties、party_edges、accounts、ledgers、freezes、model_prices、idempotency_records、grants（或扩展现有 RBAC 而非平行复制）。  
- **现有表热字段增量示例：** `api_keys.account_id`；用量/请求日志：`cost_amount`、`sell_amount`、`cost_items`（jsonb）、`account_id`、`freeze_id`。  
- 价目、策略组合、分时规则等复杂配置使用 **JSON 文档字段**。  
- 账本变更必须并发安全；流水只追加。  
- **禁止：** 为每个策略/差异原因/能力维度无限建表；宽表堆告警阈值；无流水的余额修改接口。

| 审计保留 | 调用与关键配置审计不少于 180 天；支持冷热分离 |
| 可扩展 | 新上游适配器、新 itemCode、新路由策略、新关系类型、安全钩子可扩展且不修改守恒与扣费语义 |
| 可观测 | 指标、健康检查、冻结超时与续期、幂等冲突、关键日志字段稳定可检索 |

## 9. 验收标准

### 9.1 功能验收

| 场景 | 通过条件 |
|------|----------|
| 统一接入 | 至少 5 类公有上游 + 1 类私有化兼容；上层主要改 base_url 与 Key 可调用 |
| 双轨计量 | 同一调用同时产生正确的 cost 与 sell，且分项符合价目与上游用量口径 |
| 用量规范化 | 残缺上游 usage 有标记，不出现伪造缓存明细 |
| 独立项目经费 | 无组织挂靠的项目可建账本、划拨、Key 扣费 |
| 组织费用池 | 无项目的组织账本可支持 Key 扣费 |
| 出资划拨 | sponsors 方向守恒划拨成功；反向默认失败 |
| 价格约束 | 默认 δ=0 下更贵候选被剔除；无候选时拒绝且无上游调用 |
| δ 上限与审计 | 配置 δ>20% 被拒绝；修改 δ 产生关键配置变更审计记录 |
| 额度阻断 | 冻结或余额不足时调用被拒绝并返回约定错误 |
| 冻结超时 | 过期自动解冻且有流水 |
| 流式续期 | stream 调用在网关侧自动延长冻结有效期，客户端无需续期接口；达累计上限行为符合设计且可观测 |
| 清算 | 先阻断新调用，排空冻结后到账，Key 收口 |
| 幂等 | 同一幂等键重复划拨/清算不产生第二次记账 |
| 越权 | 未授权主体日志不可读；无 fund 不能划拨；无 routing 不能改价目/密钥 |
| 调度账户 | 任意路由结果下，扣费账户仍为调用 Key 所绑账户 |
| 策略矩阵 | 可对档案启用/禁用单个策略并组合；合规硬策略不可对受限主体关闭 |
| 禁用 | 禁人后 Key 立即失效 |
| 治理 API | 关键资金与 Key 操作可通过 API 完成并鉴权 |
| 网络策略（启用时） | INTERNAL_ONLY 用户请求外网模型不产生外网流量 |

### 9.2 财务演示脚本（须可重复演示）

为某项目主体配置内部预算与内部加价；自出资方或上级划入经费；为成员创建绑定该项目账本的 Key；发起调用；核对：内部扣 sell、系统记 cost、流水与调用日志一致；导出或展示内部结余与消耗归因；演示清算回流；演示重复提交划拨请求仅入账一次。

### 9.3 非功能验收

在约定硬件与部署拓扑下完成压力与可用性测试并出具报告；安全扫描与密钥存储抽检通过；审计保留策略验证通过；目标国产环境冒烟通过；冻结超时任务与幂等窗口行为验证通过。

## 11. 明确不在范围与后续可选

**当前不在范围：**

- Agent 编排 IDE、提示词资产中心、面向 C 端的聊天产品  
- 同一请求拆到多个账本分摊扣费  
- 默认透支信用  
- 由业务客户端负责冻结续期  
- 无审计、无权限的上游密钥写入  
- 以区块链作为热路径余额主账本  

**后续可选增强（需单独需求）：** 多币种、发票与税务、更复杂审批流、与企业主数据 HR/ERP 深度双向同步、智能报价推荐、跨法人互不信任场景下的审计旁路等。

## 12. 术语表

| 术语 | 定义 |
|------|------|
| Token | 模型计费的基本用量单位及缓存、推理等衍生类型 |
| 网关 Key | 企业发给调用方的凭证，不等于上游厂商 Key |
| Party | 组织或项目等可持有账本与成员的主体 |
| 双轨 | 上游成本价（cost）与内部结算价（sell）并行计量 |
| 请求锚定内部价 | 由请求逻辑模型确定的内部 sell 基准，用于约束调度候选 |
| δ | 调度候选相对锚定内部价允许的上浮比例；默认 0，硬上限 20% |
| 预扣 / 结算 | 调用前冻结，调用后按实际内部价结清 |
| 冻结续期 | 流式进行中由网关延长同一冻结的过期时间，不增加冻结金额 |
| 清算 | 结束主体经费使命时的资金回流与权限收口 |
| 正交授权 | 数据、资金、身份密钥、调度配置分轴授权 |
| 策略矩阵 | 可启停、可混合组合的路由策略集合，非固化单一降级链 |
| 治理 API | 与管理台对等的控制面可编程接口 |
| 幂等键 | 客户端提供的去重标识，防止写操作网络重试重复记账 |
| itemCode | 与上游账单对齐的费用项编码（如 prompt_tokens） |

## 13. 总结

本产品是企业内 AI 调用的**治理与结算基础设施**：

- 以 **TokenHub** 为通路与治理底座，最小化二次开发路径；  
- 以 **AxonHub** 已验证的费用项、价目 JSON 与成本明细口径做计价融合，并强制双轨；  
- 以 **Party 平级主体 + 关系边** 适配物理世界多态经费形态；  
- 以 **Leader、守恒划拨、人 Key 扣费** 落实财务治理第一护城河；  
- 以 **可插拔路由策略矩阵** 替代固化四层，并在价格帽与账户锁定下追求降本高可用；  
- 以 **四轴正交授权、冻结 TTL 与流式网关续期、清算状态机、治理 API 幂等、薄 DDL** 守住安全与可维护性。

**核心需求与基线完整、详细、自洽、可测试、可验收。** 扩展通过适配器、策略插件、价目文档、关系类型与安全钩子完成，保证系统可迭代、可升级、可灵活扩展，且不稀释财务与安全内核。
