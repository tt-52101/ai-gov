## 0. 文档说明

本文档为独立完整的产品需求规格，描述目标系统的定位、物理世界约束、功能与非功能需求、资金与调度边界、权限模型、关键流程、数据原则、验收标准与交付分期。阅读与执行本需求无需依赖其他需求文稿。

**设计哲学：** Token 是 AI 时代的电力。本产品不运营模型供给、不对外倒卖 Token，只在企业内部提供统一接入、计量计费、资金分配与结算、安全控制与审计。目标闭环为：

> 模型接入 → 安全拦截 → 智能调度 → 实时扣费 → 资金回笼与清算 → 对账审计。

**核心公理（不可配置取消）：**

1. 无计量则无管理。  
2. 无归因则无法优化。  
3. 无企业自有调用入口则无法掌控 AI 资产与成本。  
4. 无守恒账本则无财务治理。  
5. 调度不得改变扣费账户；内部结算价格受请求锚定约束，禁止先调用后欠费。  
6. 授权按数据、资金、身份密钥、调度配置四轴正交，禁止一轴推导另一轴特权。  
7. 平台管理员也必须经账本服务与流水变更余额，不得提供绕过守恒的后门。

## 1. 产品综述

### 1.1 要解决的问题

企业规模化使用大模型时普遍存在：

- 员工与团队私自采购上游 API Key，调用黑箱，无法统一禁用与审计。  
- 财务只能拿到厂商总账单，无法按组织、项目、人员、应用做内部结算。  
- 成本失控：无预算预扣、无实时阻断、无内部结算价与上游成本的双轨可见性。  
- 合规风险：敏感数据可能经未审批路径出境；管理员改配置缺少不可篡改留痕。  
- 可用性与成本难以兼顾：多模型多渠道需要可组合的调度策略，且不得击穿账本。

### 1.2 价值主张

| 主张 | 说明 |
|------|------|
| 统一治理 | 全部模型调用经单一企业网关，消灭野连接 |
| 财务闭环 | 主动预算、预扣与实扣、主体间划拨与清算、双轨计量、对账 |
| 安全合规 | 密钥托管、出网策略、内容安全、全链路与配置变更审计 |
| 降本增效 | 在准确计量与价格约束前提下，按成本、健康、权重、会话亲和等策略调度 |

### 1.3 产品边界

**本产品负责：**

- 身份、成员、主体（组织与项目等）、正交授权  
- 上游模型与私有化资源接入、上游密钥托管  
- 调用接入、安全拦截、路由调度  
- Token 计量、双轨计价、账本、划拨、预扣结算、清算  
- 调用审计、配置变更审计、对账与成本报表  
- 管理控制台与对等的控制面治理 API  
- 运维可观测  

**本产品不负责：**

- Agent / 工作流编排、Skill 市场、面向终端用户的业务对话产品界面  
- 作为云厂商对外售卖 Token 或模型本身  

与上层系统的契约：提供 OpenAI 兼容 HTTP API（及必要的其它协议兼容面）；支持请求携带业务标签（如 user、task、agent、skill 等）用于归因。业务标签不替代鉴权，不替代扣费账户。

### 1.4 目标用户

| 角色 | 主要诉求 |
|------|----------|
| 平台管理员 / 架构师 | 部署、资源池、路由、系统配置、上游密钥 |
| 财务 / 成本控制 | 账本、划拨、加价、报表、对账、清算 |
| 安全 / 合规 | 出网、拦截、审计检索、保留策略 |
| 组织或项目负责人 | 本主体经费、成员与 Key、消耗可见 |
| 实体人 | 持有 Key、合法调用、查看本人用量 |

### 1.5 能力优先级

| 优先级 | 能力域 |
|--------|--------|
| P0 | 统一接入与密钥托管、财务治理与计量闭环、正交授权与数据不越权、调度与资金在价格与账户上的强制边界、治理 API 与关键写操作幂等 |
| P1 | 可插拔智能调度与降本、基础运营报表与仪表盘 |
| P2 | 内容安全与出网强化、配置变更快照形态强化、上游账单自动对账 |

**分期说明：** 安全扫描等具体能力可为 P2，但数据面主路径须在财务闭环阶段预留安全扩展点，避免后期全链路改造。若合同强制出境与内容安全，该项目可将对应能力提升为项目级 P0。

## 2. 物理世界模型与多态约束

### 2.1 设计出发点

真实企业中 AI 经费与编制形态是多态的。系统不得假设唯一结构「公司 → 部门 → 项目 → 人」，也不得强制「项目必须挂在某个部门下」。

### 2.2 典型场景

| 场景 | 组织 | 项目 | 关系与资金 |
|------|------|------|------------|
| 部门日常额度 | 有 | 可不建 | 部门主体持有账本，Key 扣该账本 |
| 部门主责专项 | 有 | 有 | 可用主责关系关联；项目可自有账本 |
| 公司级战略项目 | 多个事业部 | 有，可与部门平级 | 多部门出资到同一项目账本 |
| 跨主体协作 | 内外部 | 有 | 人可只加入项目、不加入内部部门 |
| 矩阵制 | 多条线 | 有 | 多协作关系；一次调用只扣一个账本 |
| 结项 | — | 结束 | 资金回流；Key 失效或改绑 |

### 2.3 统一主体 Party

组织（org）与项目（project）是同一层语义上的**主体（Party）**，均可：持有账本、拥有成员、指定负责人（Leader）、作为授权资源。

- 项目不必从属于某个组织。  
- 需要结构时用显式关系边描述。  
- 控制台可分「组织」「项目」导航，底层模型与权限引擎必须统一。

### 2.4 关系边

| 关系类型 | 含义 | 与资金的关系 |
|----------|------|----------------|
| parent | 组织汇报树 | 默认允许上级 → 下级划拨 |
| sponsors | 出资 | 默认允许出资方 → 被出资方划拨 |
| owns | 主责 / 主办 | 不自动产生划拨权 |
| participates | 协作 | 不自动产生划拨权 |

无关系时：独立项目或独立组织费用池均可成立。

### 2.5 人、Key、账本

| 对象 | 含义 | 规则 |
|------|------|------|
| Person | 实体人 | 通过成员关系进入一个或多个 Party |
| API Key | 消费凭证 | 必须绑定一个扣费账户；调用与扣费的唯一入口 |
| Account | 账本 | 归属某个 Party；记录可用余额与冻结金额 |
| Leader | 负责人 | 对本 Party 的默认责任角色，权限以显式授权为准 |

**资金流转强制规则：**

1. 划拨：一方减少、另一方增加，金额相等，同一事务。  
2. 预扣：可用余额转入冻结，必须带冻结标识与过期时间；流式场景按下述续期规则延长有效期。  
3. 结算：按实际内部价从冻结结清，多退少补。  
4. 清算：按状态机阻断新调用、排空冻结后，再回流资金并收口 Key。  
5. 任何余额变更必须有流水；禁止无流水改账；默认不允许成功路径产生负余额。  
6. 关键资金写操作必须支持幂等，避免网络重试导致重复记账。

**消费强制规则：** 内部结算金额只从 Key 绑定的账户扣除，并归因到 Key 所属实体人；业务标签只做报表归因，不形成第二套资金。

### 2.6 可迭代与扩展原则

- **稳定核心：** 计量、双轨、账本守恒、Key 扣费、四轴授权、统一入口、调度价格上限与账户锁定、冻结生命周期、清算状态机、治理 API 幂等。  
- **扩展面：** 新关系类型、新费用项编码、新路由策略、价目分时规则、安全钩子、对账连接器、划拨白名单。  
- **存储纪律：** 热字段精简；复杂结构用文档型配置；禁止为每个扩展点无限加表加列。  
- **发布演进：** 可先只计量双轨再实扣；策略可观察后再生效。

## 3. 系统架构

### 3.1 逻辑分层

```text
上层应用 / Agent
       │  兼容 API + 业务标签
       ▼
接入层：Key 鉴权 → 身份有效性 → 内容安全钩子 → 出网策略钩子
       ▼
资金层：解析账户 → 价格锚定与候选价格过滤 → 冻结（含 TTL / 流式续期）
       ▼
调度层：策略引擎选择渠道/模型（仅价格合格候选）→ 上游调用（托管密钥）
       ▼
计量层：规范化用量 → 计算 cost 与 sell → 结算 → 写审计
       ▼
控制面：Party、成员、授权、划拨清算、价目、路由、密钥仓库、对账、报表
       │
       └── 治理 API 与管理控制台（同一鉴权模型；写操作幂等）
```

### 3.2 平面划分

| 平面 | 职责 |
|------|------|
| 数据面 | 鉴权、预扣、调度、转发、结算、调用日志、冻结续期 |
| 控制面 | 配置、主体、资金操作、授权、价目、路由、密钥、审计查询 |
| 运维面 | 健康、指标、探针、备份、多实例协调、冻结超时任务 |

### 3.3 技术方向（推荐）

| 层次 | 推荐 |
|------|------|
| 后端 | Go |
| 账本与事务数据 | PostgreSQL / TiDB / OceanBase 等强事务存储 |
| 限流与短状态 | Redis |
| 异步任务 | 可选消息队列（对账、超时解冻等） |
| 日志检索 | Elasticsearch 或等效方案 |
| 监控 | Prometheus + Grafana |
| 部署 | Docker / Kubernetes；支持离线与内网；国产 CPU 与操作系统列入早期验证 |

### 4.2 双轨计价与用量计量

**费用项编码（可扩展）基线：** prompt_tokens、completion_tokens、prompt_cached_tokens、prompt_write_cached_tokens、completion_reasoning_tokens，以及厂商特定缓存 TTL 变体等。

**计价模式：** flat_fee（按次）；usage_per_unit（按单位用量，通常每 1M Token）；usage_tiered（阶梯）。

**双轨：** cost 为上游成本（对账、毛利）；sell 为内部结算价（扣账本）。

价目挂在渠道 × 模型，以结构化文档保存各费用项的 cost/sell、模式、阶梯与可选分时覆盖。

| 编号 | 名称 | 描述与规则 | 优先级 |
|------|------|------------|--------|
| PRI-01 | 价目配置 | 维护双轨价目；变更审计。 | P0 |
| PRI-02 | 用量解析 | 规范化提取各 token 类型。 | P0 |
| PRI-03 | 费用计算 | 输出 cost、sell 总额及分项。 | P0 |
| PRI-04 | 落账 | 调用记录保存双轨金额、分项、账户、人、Key、主体、标签。 | P0 |

## 5. 关键边界规则与流程

### 5.1 预扣、调度价格与结算（强制）

1. **请求锚定内部价 \(P_{request}\)**  
   由请求中的逻辑模型及价目、预估用量确定内部 sell 预估基准。

2. **候选价格约束**  
   - 候选须满足：\(P_{candidate} \le P_{request} \times (1 + \delta)\)。  
   - **默认 \(\delta = 0\)**（不得超过锚定 sell）。  
   - 仅当调度档案显式配置上浮时允许 \(\delta > 0\)。  
   - **\(\delta\) 建议上限为 20%（配置硬上限不得超过 20%）**；超过上限的配置拒绝保存。  
   - **\(\delta\) 的任何修改必须记为关键配置变更审计**（操作者、前后值、时间、档案标识），不可仅写普通操作日志。  
   - 不合格候选剔除；无合格候选则拒绝调用，返回明确错误，**不得先调用再欠费**。

3. **冻结金额**  
   在价格过滤后的候选集上，按预估 sell 的最大值冻结；候选为空则不冻结、直接拒绝。

4. **结算**  
   按实际用量与落地价目计算 sell 与 cost；从对应冻结结清；多退少补。  
   若冻结已过期或不存在：不得无依据直接扣减；调用若已成功，记补偿类流水并告警，进入人工复核。

5. **账户锁定**  
   全流程扣费账户 = 鉴权时 Key 绑定的账户，调度不得修改。

### 5.2 划拨路径规则（强制默认）

| 路径 | 默认是否允许 | 方向 |
|------|--------------|------|
| parent（组织树） | 是 | 仅上级 → 下级 |
| sponsors（出资） | 是 | 仅出资方 → 被出资方 |
| owns / participates | 否 | 不自动开通划拨 |
| 无关系双方 | 否 | 除非划拨白名单 + fund 授权 |

平级任意互转默认禁止。清算回流在清算操作中显式指定目标账户，须 fund 授权与审计。

### 5.3 冻结生命周期与流式续期（强制）

1. 每笔冻结包含：`freeze_id`、账户、金额、`expires_at`、关联 request_id（若有）。  
2. **默认初始 TTL：15 分钟**（可配置，须有上下限，例如 1–60 分钟作为单次窗口参数）。  
3. **续期责任在网关侧，不在业务客户端。**  
   - 非流式：一次请求在 TTL 内完成；超时由后台解冻。  
   - **流式（请求声明 stream=true 或等价）：** 网关在流式响应仍在进行时，**自动续期**同一 `freeze_id` 的 `expires_at`（例如每收到上游有效数据或每固定心跳间隔延长一个续期步长）。  
   - 续期不得增加冻结金额，仅延长有效期。  
   - 单次调用冻结有效期累计上限可配置（例如不超过 2 小时），达到上限则结束续期；若流仍未结束，按「冻结到期」规则处理（停止继续占用额度的路径须可观测，并避免无流水悬挂）。  
4. 后台任务扫描过期冻结：自动解冻，流水类型标识为超时解冻。  
5. 真相以持久化记录为准。

### 5.4 调用主路径

1. 客户端使用网关 Key 调用。  
2. 校验 Key、归属人、账户绑定。  
3. 安全钩子（若启用）。  
4. 计算 \(P_{request}\)；生成候选并价格过滤；按最大合格预估冻结；不足则拒绝。  
5. 在合格候选中按策略选择渠道与模型；使用托管上游密钥调用。  
6. 流式场景由网关维持冻结续期直至结束或触达累计上限。  
7. 规范化用量；计算 cost、sell；结算；写调用审计。  
8. 返回兼容响应；错误码可区分鉴权失败、额度不足、无合格路由、合规拦截、上游故障等。

### 5.5 划拨路径

1. fund 授权校验。  
2. 通道规则校验。  
3. 幂等键校验（见 5.7）。  
4. 事务内双边记账与流水。  
5. 操作审计。

### 5.6 清算状态机（强制顺序）

```text
active
  → liquidating_block_new     // 拒绝新调用与新冻结；在途可继续
  → liquidating_drain         // 等待活跃冻结清零或全部过期/解冻
  → liquidating_transfer      // 余额转入目标账户
  → liquidated                // Key 吊销或解绑；主体只读
```

存在未到期冻结时，不得将冻结占用金额当作可划转余额转走。可配置最长等待；超时仍有冻结则告警并停留在 drain。流式在途默认允许结束或直至冻结规则终止。

### 5.7 治理 API 幂等（强制）

| 项 | 规则 |
|----|------|
| 适用范围 | 至少包括：划拨、清算、冻结相关补偿、Key 创建（若会产生账务副作用的绑定）、其它会导致余额或主体资金状态变化的写接口 |
| 机制 | 客户端提供 **Idempotency-Key**（或等价请求头/字段）；服务端对「键 + 操作者 + 接口」在有效窗口内去重 |
| 行为 | 重复请求返回首次成功结果（或明确的「已处理」语义），**不得**第二次记账 |
| 存储 | 幂等记录保留合理窗口（可配置，建议不少于 24 小时） |
| 审计 | 流水或审计中可关联 idempotency_key，便于排障 |

只读接口不强制幂等键。

## 9. 验收标准

### 9.1 功能验收

| 场景 | 通过条件 |
|------|----------|
| 统一接入 | 至少 5 类公有上游 + 1 类私有化兼容；上层主要改地址与 Key 即可调用 |
| 双轨计量 | 同一次调用正确记录 cost 与 sell 及分项 |
| 用量规范化 | 残缺上游 usage 有标记，无伪造缓存明细 |
| 独立项目 | 无组织挂靠项目可建账、划拨、Key 扣费 |
| 组织费用池 | 无项目组织账本可扣费 |
| 出资划拨 | sponsors 方向守恒成功；反向默认失败 |
| 价格约束 | 默认 δ=0 下更贵候选被剔除；无候选时拒绝且无上游调用 |
| δ 上限与审计 | 配置 δ>20% 被拒绝；修改 δ 产生关键配置变更审计记录 |
| 额度阻断 | 冻结不足时拒绝 |
| 冻结超时 | 过期自动解冻且有流水 |
| 流式续期 | stream 调用在网关侧自动延长冻结有效期，客户端无需续期接口；达累计上限行为符合设计且可观测 |
| 清算 | 先阻断新调用，排空冻结后到账，Key 收口 |
| 幂等 | 同一幂等键重复划拨/清算不产生第二次记账 |
| 越权 | 未授权日志不可读；无 fund 不能划拨；无 routing 不能改价目/密钥 |
| 调度账户 | 任意路由结果下扣费账户仍为 Key 绑定账户 |
| 禁用 | 禁人后 Key 立即失效 |
| 治理 API | 关键资金与 Key 操作可通过 API 完成并鉴权 |
| 网络策略（启用时） | INTERNAL_ONLY 不产生外网流量 |

## 12. 术语表

| 术语 | 定义 |
|------|------|
| Token | 模型计费基本用量及缓存、推理等衍生类型 |
| 网关 Key | 企业发给调用方的凭证，不等于上游厂商密钥 |
| Party | 组织或项目等可持有账本与成员的主体 |
| 双轨 | 上游成本价与内部结算价并行计量 |
| 请求锚定内部价 | 由请求逻辑模型确定的内部 sell 基准，用于约束调度候选 |
| δ | 调度候选相对锚定内部价允许的上浮比例；默认 0，硬上限 20% |
| 预扣 / 结算 | 调用前冻结，调用后按实际内部价结清 |
| 冻结续期 | 流式进行中由网关延长同一冻结的过期时间，不增加冻结金额 |
| 清算 | 主体经费收口：阻断、排空冻结、回流、Key 处理 |
| 正交授权 | 数据、资金、身份密钥、调度配置分轴授权 |
| 治理 API | 与管理台对等的控制面可编程接口 |
| 幂等键 | 客户端提供的去重标识，防止写操作网络重试重复记账 |

## 13. 总结

本产品是企业内 AI 调用的治理与结算基础设施：以统一入口与密钥托管消除黑箱；以双轨计量和守恒账本实现可审计的内部金融闭环；以实体人与 Key 落实消费责任；以组织与项目同一层主体模型适配多种经费形态；以划拨通道、冻结 TTL 与流式网关续期、清算状态机、调度价格上限（含 δ 硬上限与关键审计）及治理 API 幂等，消除资金与调度路径上的模糊与重试风险；以四轴正交授权支持安全运营与自动化。

**核心需求与基线完整、自洽、可测试、可验收。** 扩展通过适配器、策略、价目文档、关系类型与安全钩子完成，保证可迭代、可升级、可灵活扩展，且不稀释财务与安全内核。
